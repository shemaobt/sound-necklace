# Noridoc: adapters/sessions

Path: @/adapters/sessions

### Overview

- The session-persistence port (ENG-240, PRD v2 §7.3): continuous full-state autosave (no explicit save action), resume from any machine, the completed/in-progress lifecycle, a single-editor advisory lock, the `respostas/*.webm` voice resources (put/get/list/delete), and — since ENG-281 — renaming and hard-deleting a session (an owner decision; §7.2 describes the dashboard and does not specify either verb). **Since ENG-702**, `complete()` no longer carries an artifact trio — the scope cut that removed the artifact builders (ENG-689/ENG-691) left nothing for it to upload; see Core Implementation.
- `SessionStore` (@/adapters/sessions/types.ts) is the port; it ships the headless `FixtureSessionStore` (default) and the real `HttpSessionStore` — the tripod-api client whose wire was verified end-to-end in ENG-267 (`http/sound-necklace.http` on the API side) — plus the reusable `createAutosaver` state machine shared by both, following the same port + real + fixture + `register.ts` shape as @/adapters/audio and @/adapters/connectivity (see @/adapters/docs.md).
- Exists so the whole app, dashboard, and every UI/E2E test run with no real backend; the real mode is selected by the composition root under `VITE_API_MODE=real` (@/ui/app/session-adapter.ts, ENG-247), fixture stays the default.

### How it fits into the larger codebase

- Consumes @/contracts DTOs (`SessionStateDto`, `SessionSummary`, `ArtifactTriple`, `LockStatus`, `SessionStep`, `ResourcePath`, `CreateSessionRequest`, `RenameSessionRequest` from @/contracts/api.ts and @/contracts/session-state.ts). It imports the connectivity port (@/adapters/connectivity/types.ts) for the offline pause; it needs nothing from @/domain and never imports `ui/` — @/.dependency-cruiser.cjs enforces both directions.
- The backend half of rename/remove is `shemaobt/shema-api` PR #153 (ENG-414) — open and green but not yet merged, so `HttpSessionStore.rename`/`.remove` are written to the agreed contract but do not exist in production yet; the app runs against `FixtureSessionStore` in the meantime.
- @/adapters/sessions/register.ts still declares the `{ port: 'sessions', fixture, real }` registration per convention (@/docs/architecture.md §4), but the app's actual wiring is the mode-aware app-global singleton `appSessionStore()` in @/ui/app/session-adapter.ts: under `VITE_API_MODE=real` it builds the `HttpSessionStore` with the browser fetch/connectivity, the logged-in editor as a `user` thunk, an **async** token gated behind `authReady()` (every session call waits for the boot resume, so a reload cannot race a 401), and `onLockLost` feeding the review chrome.
- Consumed by `ui/` only through the port and props/wiring (Setup creates, Dashboard lists/resumes/renames/removes). The listener-facing autosave freeze pairs with the connectivity gate (@/adapters/connectivity/docs.md) — losing connection pauses saving without clearing state. **Since ENG-702**, `complete()` is called from @/ui/app/App.tsx's `SessionStations`, on the Rever station's `onBlockClosed('historia')` (@/ui/pages/review) — the only caller in `ui/` today. `getArtifacts()` has no caller anywhere in `ui/`: it was reached only from @/ui/pages/export, deleted in ENG-689 (scope cut 1/4, `adapters/sessions` itself frozen and untouched by that slice), and nothing replaced that caller since there is nothing left to download — flagged for a follow-up issue rather than deleted.

### Core Implementation

- **`createAutosaver`** (@/adapters/sessions/autosave.ts) — the shared autosave machine both stores delegate to. It coalesces per session via a `Map` (last state wins), debounces bursts with `setTimeout`, retries a failed `persist` with exponential backoff, and **pauses while offline**: `drain`/`persistOne` early-return when the injected `ConnectivityMonitor` reports offline, keeping the pending state; a `subscribe` callback re-arms the timer on reconnect so nothing is lost (PRD §13). One failure is never retried: a thrown `LockLostError` (below) is terminal — the loop drops the pending state instead of holding it for a retry that would only repeat the same rejection. The persistence target is injected, so the fixture writes to its backend and the HTTP store issues a PUT. It also exposes an aggregate `onStatus(cb)` (surfaced on the port as `SessionStore.onAutosaveStatus`) that reports `'saving'` while anything is pending or in flight — including offline and retry, so the UI never claims "saved" with a write still open — and `'saved'` once everything has landed; the app's header binds this to the save-chip (ENG-351).
- **`FixtureSessionStore`** (@/adapters/sessions/fixture.ts, the DEFAULT) — built over a **shareable** `FixtureSessionBackend` (the simulated server). Two stores over one backend are two users on one server, which is what exercises the advisory lock. The backend optionally mirrors its JSON-able records (summaries/state/artifacts/lock) to a `KeyValueStorage` (localStorage shape) under `colar-de-sons:sessions:v1` and hydrates from it on construction; voice-resource bytes live in memory only. The dashboard step (`SessionSummary.progress.current_step`) is derived from the saved state's `mode`/status via `stepFor`. **Since ENG-691** the `mode: 'concluida'` branch maps straight to `save` — the terminal mode has no flag to read any more: until then the same branch read `mapeamento` and chose between `save` and `conversation` by whether the saved document carried `reviewComplete === true` (ENG-514), because `mapeamento` was the interview and its review could still be in progress. The server's own `SessionStep` enum (@/contracts/api.ts) still carries `conversation` and `save` from that lifecycle — unchanged by this cut, and unreachable from `stepFor` now that nothing writes `mapeamento` any more (@/ui/pages/dashboard/docs.md's `PAST_THE_END` still maps both onto the app's last surviving station, for a session saved by an older build).
- **`HttpSessionStore`** (@/adapters/sessions/http.ts) — the real tripod-api client, all routes under the `/sound-necklace` prefix, with an **injected** `fetch` (no network in CI). The token getter may return a Promise (the real wiring awaits `authReady()` inside it) and `user` may be a thunk (the editor is only known after login — `me` is a getter that evaluates it). JSON responses that are contract-shaped (`SessionSummary`, list, `LockStatus`) are schema-parsed; the opaque state and the WebM resource bytes travel without re-serialization. `acquireLock` and `renewLock` both `PUT /sessions/{id}/lock` — the backend serves acquire and renew as the same idempotent operation, and there is no POST on that route (it would 405).
- **`complete()` no longer carries an artifact** (§8.8, ENG-702): the session's pending autosave is cancelled **and the in-flight write is awaited** (`Autosaver.settle` — a dispatched `PUT /state` cannot be aborted, and landing after the final state would regress the saved document; `reopen` does the same), then a final `PUT` of the state, then a **bodyless** `POST /sessions/{id}/complete`. That is the whole wire now. Until ENG-702 this was a three-step multipart upload (`POST /sessions/{id}/artifacts` carrying the trio as `manifest`/`anchoring`/`report` form-data, validated against an upload receipt) that landed BETWEEN the state PUT and the completion POST; the product stopped generating that trio in the earlier scope cut (ENG-689/ENG-691), which left nothing for `ui/` to pass in — the API itself does not require one to accept `/complete` (verified against `app/services/sound_necklace/complete_session.py` in tripod-api). `HttpSessionStore.complete`'s type signature dropped the `artifacts: ArtifactTriple` parameter to match (@/adapters/sessions/types.ts); the `ArtifactTriple`/`ArtifactKind` types and the multipart-upload machinery are otherwise untouched by this change — they still back `getArtifacts` below, which nothing calls any more.
- **`getArtifacts` and its download path are orphaned, not deleted.** `getArtifacts` issues one GET per kind; the route answers 307 to a signed URL and `fetch` follows it alone — the browser strips the `Authorization` header on the cross-origin hop (fetch spec), which the signed URL requires. It compiles and is still exercised by this module's own tests, but no caller remains in `ui/` since `complete()` stopped populating any artifact to fetch — `FixtureSessionStore.complete` (@/adapters/sessions/fixture.ts) no longer sets `rec.artifacts`, so a fixture-mode `getArtifacts` call after `complete()` now always throws `SessionNotFoundError`. Flagged for a follow-up issue rather than removed. `getResource` is a separate, still-live download path (voice-resource bytes, unrelated to the artifact trio): an explicit two-hop, `GET /resources/url?path=…` (with Bearer) returns the signed URL, then a second fetch **without** Bearer (an `Authorization` header alongside the signature is a 400 on GCS). Resource writes/deletes address the path via the `?path=` query (`putResource`/`deleteResource`); `listResources` lists the whole session and filters the prefix client-side.
- @/adapters/sessions/index.ts is the public barrel for the wiring layer and tests; only the composition root imports the implementations (to build the app-global singleton in @/ui/app/session-adapter.ts) — stations resolve the store through their `ports.ts` defaults, never by importing a class.
- **`rename`/`remove`** (ENG-281) are the two user-initiated session-management verbs the Dashboard's kebab menu will drive (that UI is a separate slice; this port change only teaches the store the verbs). `rename` changes ONLY `SessionSummary.story_name` — the request/wire body carries a single `story_name` key (`RenameSessionRequestSchema`, @/contracts/api.ts) and `story_slug` is never sent and never changes: the slug names the three artifact files (§10.6 — §10.5 is opaque custody, and the backend's own docstrings mis-cite it) and anchors the ENG-253 byte-identity acceptance, so a rename that carried it would rename the exported artifacts. Both stores parse the name through `RenameSessionRequestSchema`, whose `trim`/`min(1)`/`max(255)` mirror the server's `StringConstraints` exactly — the fixture must not store `"  Oi  "` where the real mode stores `"Oi"`, and the fixture bumps `last_modified` because the server's `updated_at` is `onupdate=func.now()` and the dashboard sorts by it. `remove` is a hard delete — summary, state, artifacts and the session's voice resources all go together — available at any time, including on a completed session; duplicate was explicitly ruled out of scope. `FixtureSessionStore` implements both directly against its backend map; `HttpSessionStore.rename` is `PATCH /sessions/{id}` (response reparsed through `SessionSummarySchema`) and `.remove` is `DELETE /sessions/{id}` resolving on a bodyless 204, cancelling any pending autosave for that id **only after** the 204 — cancelling first would discard unsaved state on a refusal, leaving the session alive on the server without the edits.

### Things to Know

- **Custody is opaque (§10.5):** the fixture deep-clones (`structuredClone`) both in and out and never re-serializes or reinterprets the payload shape; `HttpSessionStore.load`/`getArtifacts` return the raw payload as-is (deep validation is the state layer's job, not the store's). Until ENG-691 this byte-identity was also what kept the golden harness green; that harness is gone (@/domain/docs.md), but the custody rule itself is unrelated to it and still holds for the session-state document this layer actually round-trips today — the ONLY document, since ENG-702 stopped `complete()` from carrying an artifact trio.
- **Acquiring or reading the lock never throws on conflict.** `acquireLock`/`renewLock`/`lockStatus` all return a `LockStatus`; if `holder` belongs to someone else, the caller opens review-mode (§7.3). Every `SessionStore` exposes its own editor identity as `me` so a caller can compare `holder.user_id` against it without knowing the mode (fixture/HTTP) or importing a fixture constant. The fixture's lock is per-user with a TTL (`lockTtlMs`, default 30s) and self-expires if the holder disappears — `#heldByOther`/`lockStatusOf` treat an expired lock as free; the real backend's lease (ENG-262) is a fixed 60s, renewed by the same `PUT` used to acquire.
- **Two different 409s live on the state PUT, and the body's `code` separates them** (fencing, ENG-262). `HttpSessionStore.#send` parses the error body into `ApiError.body`; the autosave `persist` treats only `code: 'SESSION_LOCKED'` as the verdict — it reports once via `onLockLost(id, holder)` (autosave is fire-and-forget, so the callback is the only way the UI learns; `holder` is the body's `holder_name`, null if absent) and rethrows `LockLostError` (which carries the same `holder`), terminal for `createAutosaver`: no retry, pending state dropped. `SESSION_LOCK_CHANGED` (the lease lapsed mid-write) and any 409 without a known code stay **transient** — retried with backoff exactly like a 5xx. `complete`/`reopen` skip the translation: a 409 there reaches the caller as the raw `ApiError` (@/adapters/api).
- **`rename`/`remove` share a smaller, separate translation** (`sessionWriteError` in @/adapters/sessions/http.ts, not the autosave `persist` path above): a 404 becomes `SessionNotFoundError`, a 409 carrying `code: 'SESSION_LOCKED'` becomes `LockLostError` with the body's `holder_name`, anything else rises as the raw `ApiError`. These two verbs are also the ONLY fixture writes fenced by the advisory lock (`#requireEditable` in @/adapters/sessions/fixture.ts throws `LockLostError` when another user holds it) — the autosave `#persistState` and every other fixture write still apply unconditionally regardless of lock holder; only the real backend fences the state PUT via the `code` above. The fixture fences rename/remove specifically so a permissive fixture never teaches the UI a lock-defying behaviour the real mode refuses.
- `load`/`getArtifacts` on a session that was never saved/completed throw `SessionNotFoundError` (also raised for an unknown id), the typed surface the UI shows copy for.
- Both stores' `autosave` schedule a **clone** of the state (`structuredClone`) so a later caller mutation cannot rewrite an already-queued save; the coalescing map still lets a genuinely newer `autosave` win.
- `flush` and the autosaver are **no-ops while offline** — a forced flush on navigation only persists when online; the pending state waits for reconnect.
- The fixture's `latencyMs`/`#settle` inject optional per-op delay for realistic wiring tests; tests otherwise drive the autosaver with fake timers (debounce/backoff are `setTimeout`-based).
- Fixture-safe adapter PRs may merge autonomously on green (unlike @/domain and @/contracts).
