# Noridoc: ui/app

Path: @/ui/app

### Overview

- The composition root and wiring layer of the Shemá app (ENG-224): the only place that imports adapters, @/domain, @/ui/state and @/ui/organisms together. It is the durable shell — station/adapter/addon issues almost always land purely by ADDING files under @/ui/pages, @/adapters or `ui/app/addons`. **Since ENG-689 (scope cut 1/4) every station receives the SAME `stationProps` shape** (`player`, `sound`, `onBlockClosed` — see Core Implementation): the one-time exception that used to wire the Export tail with shell-held ports (ENG-270 — the sessions store + `sessionId`) left with Export, and nothing has needed a per-station exception since.
- Owns the app frame (@/ui/app/header.tsx brand + sound toggle), the whole-story progress band (@/ui/app/story-progress.tsx, ENG-648 — the only progress chrome since ENG-668 retired the "fio de contas" dots), the single itinerant player (now with a live audio `Player` built per-session, ENG-275), review/lock chrome, the online-only connection gate, and the station host — all mounted from @/ui/app/App.tsx. It also wires the three resilience seams into the running session view (ENG-277): offline (window `online`/`offline` events), mid-session auth expiry (→ `/login`), and an advisory lock held by another editor (→ review chrome).
- The chrome was realigned to `docs/design/Colar de Sons - Protótipo.dc.html` (CLAUDE.md precedence rule 2), then extended by the v4 prototype — `docs/design/prototype.html` since ENG-647 landed it; every "v4 prototype, line N" below is a line of THAT file (ENG-648): a 64px icon-only header with a "← Histórias" pill and a 46px band carrying the current station's NAME above the whole-story progress bar. Both are documented in detail below. The prototype computes a `stepDefs`/`steps` array and never draws it, and ENG-668 followed it: the 28px row of stepper dots that used to sit under the band is gone, leaving ONE progress indicator on screen instead of two.
- App entry chain: @/index.html → @/ui/app/main.tsx (loads the token side-effects once, and imports @/ui/i18n for its init side effect **before the first render** — without that import every screen renders raw translation keys) → @/ui/app/App.tsx.

### How it fits into the larger codebase

- Outermost wiring layer of the atomic-design ladder documented in @/ui/docs.md. Per @/.dependency-cruiser.cjs it may import everything (adapters, domain, state, organisms); atoms/molecules/organisms below it may not reach back up.
- **Owns the three add-a-file registries** (@/docs/architecture.md §4), created once in @/ui/app/registries.ts and never edited again:

  | Registry | Glob                      | Builder                | Keyed by       |
  | -------- | ------------------------- | ---------------------- | -------------- |
  | Stations | `/ui/pages/*/index.tsx`   | `buildStationRegistry` | directory name |
  | Adapters | `/adapters/*/register.ts` | `buildAdapterRegistry` | port name      |
  | Addons   | `/ui/app/addons/*.tsx`    | `listAddons`           | sorted by path |

  This is the loop's no-file-conflict guarantee: landing a station, adapter, or overlay = adding files, never touching a shared registry. The pattern is proven: the first addon (@/ui/app/addons/tutorial.tsx, the tutorial popup, ENG-231) landed without editing a single shell file.

- Reads domain decisions through @/ui/state stores (never mutating @/domain directly): `useSessionStore`/`useAppStore` supply session state, the review/lock/online gate flags, and the sound toggle. Stations advance from inside themselves — each publishes its own nav footer — and the shell no longer dispatches `setMode` at all: the dots were its only caller (ENG-668).
- Subscribes the `connectivity` adapter port (fixture default, @/adapters/connectivity) and mirrors online state both into a local flag for @/ui/organisms/connection-gate and into the session store, which pauses editing when offline.

```
index.html → main.tsx → App.tsx (composition root)
   ├─ Header (brand + sound toggle → appStore)
   ├─ StoryProgress (station name + whole-story bar, story-progress-model
   │                 + stepper-model ← domain modeLocks)
   ├─ ReviewBanner (review/lock chrome ← sessionStore)
   ├─ PlayerSlotProvider (the one traveling player)
   │    └─ ConnectionGate (online) → StationHost → ui/pages station
   ├─ BreakSuggestion (a pausa sugerida, session view only)
   ├─ GoalReached (a meta de hoje alcançada, session view only)
   ├─ BlockDone (o fim de bloco, session view only)
   └─ AddonsLayer (ui/app/addons overlay chrome)
```

### Core Implementation

- **Router** (@/ui/app/router.tsx): a minimal History-API router — react-router is out of scope. `matchRoute` resolves `/login`, `/dashboard` (also `/`), `/setup`, `/session/:id`, else `unknown`. `navigate()` calls `pushState`/`replaceState` and then notifies subscribers by hand, because pushState never fires `popstate`; `subscribe` additionally listens for `popstate` (browser back/forward). `usePathname`/`useRoute` read through `useSyncExternalStore` with `location.pathname` as the snapshot (a primitive, so `Object.is` comparison is stable).
- **The real-mode switch** (@/ui/app/api-config.ts, ENG-247): `VITE_API_MODE`/`VITE_API_BASE_URL` are read ONCE here by the composition root — adapters never read env, they receive baseUrl/token injected. Every app-global singleton keys off `API_MODE`: auth (@/ui/app/auth-adapter.ts), sessions (@/ui/app/session-adapter.ts), bucket (@/ui/app/bucket-adapter.ts — which also resolves the facilitator's project via `my-project-roles`, caches it for the tab, and for multi-project accounts keeps the first project that actually has bucket audio; a platform admin gets an empty `project_roles` back for the same reason `my-roles` is empty for them — see @/adapters/api/docs.md — so `resolveProjectId` falls back to `listAllProjectIds()` over `GET /projects` before the same audio probe runs) and the session audio engine (@/ui/app/audio-player.ts). Fixture remains the default, keeping tests/CI networkless. (`@/ui/app/voice-adapter.ts`, the per-session voice store this list used to also carry, was deleted in ENG-689 along with the interview.)
- **The itinerant player** (@/ui/app/player-slot.tsx, PRD §8.0 / redesign §5.2): there is ONE player instance that travels to the active station's slot. Because changing a `createPortal` container remounts the subtree (react#12247), the player node lives in a persistent detached `holder` div (lazy `useState` init) that the portal always targets; the holder is MOVED between `PlayerHost` slots via `appendChild` (append moves, does not clone) in a `useLayoutEffect`. Placement runs through refs (no `setState` during commit), so a late-mounting lazy station host still receives the player. On active-station change it calls `player.stop()` — fed `player ?? NO_PLAYBACK` (a module-level no-op `{ stop() {} }`) so navigating between stations still stops audio, mirroring the reference `setMode`→`stopPlayback`.
- **The session audio player** (@/ui/app/audio-player.ts + @/ui/app/App.tsx `useSessionPlayer`, ENG-275/ENG-247, PRD §8.2): the composition root builds the actual audio `Player` for the active session and threads it to the necklace station. `buildSessionPlayer(sessionId)` re-decodes the session's bucket audio (`meta.bucketAudioId` from the persisted DTO via `appSessionStore().load`, bytes fetched through the mode-aware `appBucket()`), builds the `Player` with the session's locked `beadSec` on the engine the mode dictates — real: @/adapters/audio `WebAudioEngine`, whose AudioContext clock drives itself; fixture: `FixtureAudioEngine` plus the clock bridge — and rejects if the session has no saved state or the bucket audio does not resolve. `startClockBridge(transport)` (fixture-only need) drives the `FixtureTransport` — whose clock only advances on `advance()` — from `requestAnimationFrame` using the real inter-frame delta, so playback progress + `onHead` (and thus the necklace `data-play` playhead) advance in the running browser (Playwright ticks rAF); it returns a canceller. `useSessionPlayer` rebuilds on session change and, on cleanup, stops the player + cancels the bridge; a session whose audio can't resolve degrades to a dormant `null` player (stations already handle `player = null`).
- **The station model, five stations and a real terminal one** (@/ui/app/stepper-model.ts): `stepperStations` derives five station states (Ouvir · Cortar · Triage · Frases · **Rever**, ENG-725) from domain `modeLocks()` (@/domain) plus mode/flow position — down from six to four in ENG-689 (scope cut 1/4, which removed Conversa and Guardar along with the interview and export), then back up to five when ENG-725 gave the terminal domain mode its own station. `state` is done/current/future by flow index; `reachable` mirrors the gates (`[true, whole.confirmed, locks.triagem, locks.segmentacao, state.mode === 'concluida']`) — the fifth entry has no `modeLocks` key to mirror, because reaching `concluida` (the mode itself) IS what makes Rever reachable. **The domain `Mode` type changed under this station model in ENG-691 (scope cut 2/4):** it is now `escuta | triagem | segmentacao | concluida` — `mapeamento` (the interview mode) is gone, replaced by `concluida`, the terminal mode `confirmFrasesDone` writes when the last productive scene's phrasing closes (@/domain/phrases.ts). `currentIndex` maps `concluida` to the Rever station index (4): the domain-level meaning behind that transition — "no more scenes left to segment" — is unchanged from before ENG-691, only the mode's name changed; ENG-725 is what gave the shell a station to mount for it instead of reading it as the tail end of Frases. The module SURVIVED the dots (ENG-668) because it answers two questions the shell still asks: which station key to mount, and which name the progress band announces. `reachable` still has no reader — kept as the derivation's other half rather than half-deleted from a frozen-adjacent shape. The station `key` doubles as the @/ui/pages directory name the station registry resolves.
- **The band is what a screen reader hears** (ENG-668). The retired `<ol>` was the only element in the DOM that named the six stations, and both layers of the bar were `aria-hidden` precisely because it existed. The band replaced it with less, not more: `.cds-story-progress` is a `<section aria-label>` (`shell.progressAria`, the renamed `shell.stepperAria` — same words, honest name) and the station name inside it is a `role="status"` live region, so the CURRENT station is reachable by landmark at any time and a CHANGE of station announces itself. The region is mounted with its text already in it, which is deliberate: a live region created together with its message is not announced, and on arrival there is nothing to announce yet. @/ui/molecules/story-progress-bar stays `aria-hidden` — giving the track a progressbar role would put a percentage in the ear, which is exactly the counting PRD §9.2 keeps off the screen.
- **The whole-story progress bar** (@/ui/app/story-progress-model.ts + @/ui/app/story-progress.tsx + @/ui/molecules/story-progress-bar, ENG-648, v4 prototype lines 269-277/1644-1668; rescaled by ENG-689 then again by ENG-725): one thin bar under the header showing how far the WHOLE story has come — not how far the current station has come. The band is 46px: the current station's name (uppercase, announced — see the bullet above — from the same `stations.*` keys the station model emits) above a 480px/56vw track carrying the fill, stage dividers, a marker and — since ENG-653 — the goal mark. The progress half of `storyBarValues` weights the FIVE stations `STATION_WEIGHTS = [10, 22, 20, 36, 12]` (summing to 100, dividers at `STAGE_BOUNDARIES = [10, 32, 52, 88]`) and adds the current station's weight × its own completion fraction: heard beads ÷ total beads (Ouvir), scenes ÷ 5 (Cortar), non-`pending` scenes ÷ scenes (Triagem), productive scenes with ≥1 phrase ÷ productive scenes (Frases). **Rever (index 4) has no sub-step** — `stationFraction`'s default case always returns 1, so simply entering it fills the whole bar to 100. Completed stations count their full weight, so the bar never walks backwards on a station change. ENG-689 first rescaled the prototype's original six weights `[8, 14, 12, 26, 32, 8]` (which included Conversa and Guardar) down to the four survivors; ENG-725 rescaled again to open a slice for Rever, keeping the four working stations' proportions to each other from before. **Every one of those is a division and several denominators are zero in a real session** (no scenes, no productive scenes) — the module has exactly two division gates, `ratio()` for progress (returns 0 for a non-positive denominator) and `share()` for the goal (floors the denominator at 1), and `StoryProgressBar` clamps again before the value reaches a CSS `width`, because a `NaN` there is not an error, it is a bar that silently does not render. The arithmetic sits in `ui/app` for the same reason `stepper-model.ts` does: it is view derivation over `SessionState`, and the shell is the only layer that sees both the domain state and the view-local facts (how much was heard). It is NOT domain — the weights are a design choice, not a PRD rule, and nothing here reaches an artifact.
- **One fraction cannot be read from `SessionState`** and arrives through @/ui/state's `progressStore` (ENG-648): how much of the story has actually been HEARD (@/ui/pages/listen publishes the size of its cumulative heard-bead set on every new bead). It is not a domain decision and it never enters an artifact, so it does not belong in the session DTO. `StoryProgress` subscribes to that store ITSELF rather than taking the number as a prop: Escuta 1 publishes on every new bead during playback, and subscribing in `SessionStations` would re-render the whole open session — station, player provider and all — several times a second. `SessionStations` resets the store on mount (it is remounted by `key={sessionId}`), so one session's progress never opens the next one already advanced. A second fraction — artifacts DOWNLOADED, published by the Export station whenever its `downloaded` map changed — used to live in the same store; it left with Export in ENG-689.
- **Review/lock chrome** (@/ui/app/review-banner.tsx, PRD §8.10 / §7.3): renders the review banner and "Destravar para editar" when in review with no foreign lock; when another editor holds the advisory lock it shows "sessão em uso por <name>" and offers no unlock (the lock forces review). A lock with no holder name (`{ holder: null }`, @/ui/state/docs.md) renders a distinct "reconnecting…" message instead — @/ui/app/use-editor-lock.ts's renew deadline expired without an answer, or a 409 SESSION_LOCKED arrived without a `holder_name`. State comes from the session store.
- **Non-session route → station resolution** (@/ui/app/App.tsx): `login`/`dashboard`/`setup` resolve the same-named station; an `unknown` top-level path resolves the station named by its first path segment (so `/imports`, whose station lands in ENG-248, renders once its folder exists) and otherwise falls through to the station host's "em construção" placeholder. This is what makes `/setup` reachable now that the router matches it — the dashboard's "Comece uma nova história" card navigates there and lands on the Setup station.
- **Session rehydration + continuous autosave** (@/ui/app/App.tsx `useSessionHydration`, PRD §7.3): on `/session/:id` with an empty in-memory @/ui/state (a browser reload or a resume-from-dashboard, where Setup never populated the live store), it `load`s the persisted DTO from the app-global store and injects `fromSessionDto(dto).state` into `sessionStore`, so the session resumes at its current step instead of stranding on "carregando a sessão…". A `loadedId` ref guards against reloading over a live session (Setup already loaded the freshly-created one) and re-runs when the route id changes. In the same step it **wires the autosave port** (ENG-273): `sessionStore.setAutosave(live => appSessionStore().autosave(routeId, toSessionDto(live, meta)))`, so from then on every domain mutation persists the WHOLE state under this session's `meta` (granularity/audio/consent, captured from the loaded DTO) — without this, only Setup's initial DTO and completion were ever written, and a reload resumed on Escuta 1 losing all decisions. `useAutosaveFlush(routeId)` flushes the adapter's debounced queue on `pagehide` (reload/close) and on session change, closing the debounce window so the last decision is never lost. The hook returns a plain `ready: boolean`, and @/ui/app/App.tsx mounts no station while it is false (ENG-511) — that gate is not cosmetic, @/ui/state is NOT cleared between sessions, so mounting immediately rendered the PREVIOUS session's station under the new session's route until hydration landed. A load that FAILS settles too, so the placeholder never waits forever. **`toSessionDto` dropped its third argument, `reviewComplete`, in ENG-691:** since ENG-689 it was always written `false` — it used to be `reviewIsDone(live, meta.voice)`, a flag computed by @/ui/app/resume-placement.ts (deleted then, see Things to Know) that told the API whether the report's review was fully confirmed. ENG-691 went further and removed the field itself from @/contracts/session-state.ts's DTO/schema (now `schema_version: 4`, no migration — see @/contracts/docs.md): there is no review left to describe, and the frozen layer finally caught up to that fact instead of carrying a dead argument.
- **The lock has ONE owner** (@/ui/app/use-editor-lock.ts, ENG-299 / ENG-247, PRD §7.3): `App` mounts `useEditorLock(routeId)` on session routes, in BOTH modes (the fixture serves locks too — one code path, not two). It is the acquire → heartbeat → release side of the tripod-api lease (ENG-262: `PUT /sessions/{id}/lock` acquires AND renews, 60s TTL). Acquiring against a foreign holder opens review (`setLock({ holder: <name> })`, the "sessão em uso por" banner); otherwise it renews every `HEARTBEAT_MS` (15s) with +0–20% jitter — deliberately NOT client-go's `JitterFactor` of 1.2, which multiplies a 2s retry period; applied to a 15s heartbeat that would allow beats up to 33s and blow the 60s TTL after two misses. A renewal that comes back held by someone else (or by nobody) demotes immediately, without waiting for a write to be refused. A separate `RENEW_DEADLINE_MS` (45s) is re-armed only by a SUCCESSFUL renewal; if it fires, the client demotes ITSELF to review (`setLock({ holder: null })`) without waiting for a 409 — that is what actually closes the two-editor window, since nobody else can take the lease before the 60s TTL anyway. A FAILED acquire (network, transient 5xx) is not final either (ENG-338): it parks the session in review with the reconnection banner and then retries while the route stays mounted, waiting `ACQUIRE_RETRY_MS` (2s) and doubling up to `ACQUIRE_MAX_RETRY_MS` (30s) — a recursive-`setTimeout` backoff, and never a `setInterval`, which would pile attempts up on a slow network. The first success promotes exactly like a fresh acquire, heartbeat and deadline included. A foreign holder is NOT retried — that is not a failure, it is the session being in use. Release fires on unmount and on `pagehide` (best-effort — a DELETE fired as the page unloads is usually cut off; the 60s TTL is what actually reclaims a closed tab, `pagehide` only speeds up the common in-SPA case of switching sessions). `useSessionHydration` consequently does NOT touch the lock anymore — it only resets `setReview(false)` per (re)hydration so one session's review flag cannot leak into the next in-SPA; the one-shot `lockStatus` read that used to live there was removed when this hook was wired, because both wrote the same `setLock`/`setReview` and would race. The second half of the circuit is `onLockLost` in @/ui/app/session-adapter.ts: an autosave refused with 409 SESSION_LOCKED calls `setLock({ holder })` with the usurper's name from the response body.
- **Mid-session auth expiry** (@/ui/app/App.tsx `useAuthExpiry`, ENG-277, PRD §7.1): subscribes the app-global `appAuth().onAuthExpired(() => navigate('/login'))`, so a server token expiring on ANY route — `/session/:id` included — routes back to login WITHOUT touching the in-memory session state (re-login resumes at the same step). Previously this was wired only in the dashboard page, so expiring mid-session did nothing.
- **Station host** (@/ui/app/station-host.tsx): resolves the active station from the registry; a not-yet-built station falls back to a quiet "estação em construção" line, so a station issue enters purely by adding its `ui/pages/<station>/` folder. It accepts optional `stationProps` and forwards them to the resolved component. **Since ENG-689 (scope cut 1/4) that shape is uniform across all five stations**: `SessionStations` (@/ui/app/App.tsx) builds ONE `stationProps` object — `{ player, sound, onBlockClosed }` — and passes it to whichever station is current, rather than special-casing individual stations. `player` is the `Player | null` from `useSessionPlayer` (§8.2, ENG-275; stations already handle `null`), threaded to every necklace station (listen/cut/triage/phrases/review) so they play beads/edges/scenes; `sound` is the `UiSound` port, needed by every station's own click/error decisions (§9); `onBlockClosed` is how @/ui/pages/triage and @/ui/pages/review report a structural boundary closing (see the block-done entries below) — @/ui/pages/phrases still calls it too, but `SessionStations` now filters that particular call out (see below), since ENG-725 made @/ui/pages/review the next station rather than the end of the flow. The per-station wiring this bullet used to describe — `{ store, sessionId }` injected only when Export was current (ENG-270), `{ recorder, player, stt, sessionId, overlayBusy, onModePickerChange }` injected only when Conversation was current (ENG-327/ENG-649), and the `voice` recorder built from @/adapters/voice — left with those two stations. The `SessionStations` child no longer holds a `viewingExport` flag either: with Export gone, a station is reached by `setMode` alone, and there is no gate-bead click to intercept and no reachable tail to land on instead. `useSessionClock` (@/ui/state/session-clock.ts) still pulses here — the shell is the only place that knows which session is open — but nothing reads its frozen total any more; the screen that used to (Export) is gone, and the clock keeps running because @/ui/state is a frozen-adjacent layer this slice did not touch.
- **Header** (@/ui/app/header.tsx, realigned to the Protótipo's 64px band): icon-only left side — a "← Histórias" pill (`onBack`, wired to `navigate('/dashboard')` in @/ui/app/App.tsx) plus a bare `ColarIcon` (the site mark; it replaced the `ShemaIcon` that used to be painted wholesale from `--cds-chrome-mark` — a multi-colour drawing cannot take a single fill, so `header.css` now repaints only its cord and end beads, from `--cds-chrome-fg`, which is olive on a light station, cream on the ceremonial olive ones, and body-ink under the dark theme), no eyebrow/title/subtitle text (those were removed; the app name now lives only on the Dashboard). The right side keeps the sound toggle (`aria-pressed`, flips `appStore.muted`; as of today nothing else reads that flag) and, since ENG-391, the light/dark theme button beside it (moon in light, sun in dark; the accessible name states the destination, not the state). The theme button is prop-driven exactly like the sound one — `theme` + `onToggleTheme` come from @/ui/app/App.tsx — and it renders ONLY when `onToggleTheme` is supplied, so `Header` never shows a control that does nothing. Both are v2-only chrome, constrained by nothing in the frozen layers. **The language toggle used to live here and was removed in ENG-371:** a one-click PT/EN switch beside the sound control invited flipping mid-session, and the UI language used to also govern the interview voice and the locale sent to STT (both gone since ENG-689) — the underlying reason to gate it off the header, mid-session copy staying stable, still holds regardless. The choice now lives in @/ui/pages/settings, beside the project's granularity. **ENG-375 then removed the Settings entry from this header too:** the header is mounted on every station, so an entry here was reachable mid-session and undid the very friction ENG-371 created. The only way in is the gear on the Dashboard — which replaced that screen's own copy of the language toggle. **It is NOT mounted on every route:** `ownsHeader` (@/ui/app/App.tsx) suppresses it on `login` and `dashboard` (ENG-278) — both are full-bleed surfaces that ship their own header. Those two routes consequently have no sound/back toggle: they are facilitator surfaces with no playback, while every station keeps it.
- **Dark chrome variant is CSS-only, no prop-drilling** (@/ui/app/app.css): the header and the progress band read chrome colors from `--cds-chrome-*` custom properties set on `.cds-app`. `.cds-app:has(.cds-listen)` overrides those properties to the dark (cream-on-olive) palette; every other station falls through to the light default. Because the selector keys off the STATION'S OWN root class being present in the DOM, a station never needs to notify the shell of its "ceremonial" status. The progress bar's own two shades ride along as `--cds-chrome-progress-track`/`--cds-chrome-progress-line`, defined in every variant; its fill and marker halo reuse `--cds-chrome-accent`, and the marker itself is cream in BOTH themes (the v4 prototype pins it), so it is the one hardcoded colour in the molecule. **A second `:has()` clause, `.cds-app:has(.cds-conversation-stage)`, is dead CSS since ENG-689** — the class it matches was the Conversation station's, and that station is deleted, so the clause now matches nothing; the sheet itself was not part of this cut's scope.
- **Light/dark theme** (@/ui/app/theme.ts + @/index.html + @/ui/tokens/tokens.css, ENG-391): the theme lives in a `data-cds-theme` attribute on `<html>`, not in React state — `App`'s `useTheme` keeps a copy only so the header knows which glyph to draw. Precedence is stored explicit choice → `matchMedia('(prefers-color-scheme: dark)')` → light, and `initTheme()` deliberately **never writes**: persisting on boot would freeze a user who never chose to whatever the OS said the first time. `readTheme()` reads the attribute before falling back to that precedence, which is what keeps the toggle working in a window where `localStorage` throws (locked private window, exceeded quota — every storage access is wrapped). What actually repaints is the `--cds-ui-*` semantic role layer in @/ui/tokens/tokens.css; the brand and scale tokens above it are identical in both themes. **This issue shipped the plumbing only — component stylesheets still read the brand tokens directly, so switching to dark today changes native scrollbars/form controls (via `color-scheme`) and little else until the migration pass lands.**
- **Today's goal, and the mark on the bar** (ENG-653, v4 prototype lines 343-349/870-883/1030/1372-1379; rescaled by ENG-689, re-anchored by ENG-725): the facilitator picks on Setup how far the pair mean to get today, from FIVE options (`twoScenes`/`fourScenes`/`triage`/`phrases`/`wholeStory` — a sixth, `twelveTalks`, left with the interview); `storyBarValues` turns that pick into a percentage on the SAME 0-100 track, and `StoryProgress` hands it to the bar as a fixed mark. The percentage is recomputed **every render** by design — the scene count grows as the work goes on, so "2 cenas" walks left as scenes appear. That is also the performance trap ENG-648 fell into, so the model has ONE entry point: `storyBarValues(input, goal)` computes progress and goal together, cheaply now that there is no `questionSequence` walk left to defer. The anchors are derived, not copied: `TRIAGE_END` (`STAGE_BOUNDARIES[2]`, 52) is the end of Triagem and `PHRASES_WEIGHT` (`STATION_WEIGHTS[3]`, 36) is the Frases band's own width, so mark and fill cannot drift into different coordinate systems. **"Fechar as Frases" and "a história toda" still resolve to the exact SAME mark, 100** (unchanged in spirit since ENG-689, re-derived under ENG-725's new weights) — reaching Rever fills the bar to 100 (see the bar bullet above), so both goals still complete in the same instant, at the story's actual end rather than at the end of the Frases band (88). `sceneCount` falls back to 4 when the session has no scenes and is floored at 1 — without the fallback `2/0` saturates at 1 and "2 cenas" would land exactly on that same 100, yet another goal crowding the one mark, with no `NaN` anywhere to give it away.
- **Who notices the goal was reached** (ENG-653): `StoryProgress`, because it is the one place both numbers meet. It reports the STATE (not an event) through `onGoalReached: (reached: boolean) => void`, so the shell can pass a `useState` setter directly — stable identity with no `useCallback`, which is what lets the React Compiler keep memoizing the band. The comparison carries the prototype's `- 0.01` slack, since the two sides come from different roundings.
- **One full-screen surface at a time, in BOTH directions — three surfaces** (ENG-653). `SessionStations` holds `goalReached` (from the bar) plus `goalOpen`, `breakOpen` and `blockOpen` (each organism reports its own open state through `onOpenChange`) — and crosses them: the break gets `busy={goalOpen || blockOpen}`, the celebration gets `busy={breakOpen || blockOpen}`, and the block-done screen gets `busy={breakOpen}` (see the precedence note below for why it is short by one term, not zero). The mechanism is the `onOpenChange`-style callback that makes an exclusion symmetric, since a self-latching organism is otherwise invisible to the shell. All three treat `busy` as "defer, never swallow": a goal crossed mid-break opens as soon as the break closes. **A fourth surface, the conversation mode picker, joined this exclusion in ENG-649 and left with the interview in ENG-689** — the `modePickerOpen`/`overlayBusy`/`onModePickerChange` wiring it needed, and the app-global `recording` mic flag every `busy` value used to also read (it disabled the header's "← Histórias" too, ENG-393), are both gone: @/ui/state/app-store.ts dropped `recording` because the interview recorder was its only producer, and @/ui/app/header.tsx's `backDisabled`/`onBackBlocked` props are still there but nothing passes them any more.
- **The suggested break** (ENG-650): `SessionStations` mounts @/ui/organisms/break-suggestion, the once-per-session rest suggestion (PRD-redesign prototype "PAUSA SUGERIDA"). The shell supplies `busy={goalOpen || blockOpen}` and `onTakeBreak`, which is `navigate('/dashboard')`: the identical exit the header back pill uses, so the session is autosaved and resumable either way. Placement carries three of the four "never interrupt" guards for free: mounted INSIDE `SessionStations`, it does not exist on the waiting screen (which replaces that subtree wholesale), it does not exist outside a session, and the `key={sessionId}` remount re-arms the one-shot latch whenever a session is started, resumed or reopened for review. The threshold, the latch and the settle window all live in the organism; the shell holds no timer.

- **The end of a block of work** (ENG-651; the third trigger and the shift in what "the end" means added by ENG-725): `SessionStations` also mounts @/ui/organisms/block-done, the screen that marks a structural boundary. The shell holds the whole trigger, in one `useState<ClosedBlock | null>`, and that placement IS the feature: the station that confirms is precisely the one leaving the screen, so it cannot hold the state; and a session reopened past a boundary mounts this `null`, so the screen never replays on resume, on remount or on a re-render (`key={route.id}` on `SessionStations` is what makes it die with the session and only with the session). The stations hand triggers up through one `onBlockClosed` prop in `stationProps`, and **every one reads the answer from @/domain rather than re-deriving it in the UI**: @/ui/pages/triage announces `'triagem'` only when `setMode` actually moved the session to `segmentacao`; @/ui/pages/phrases announces nothing any more: `confirmFrasesDone` returning `kind: 'finished'` (the domain's own name for "that was the last productive scene") just moves the mode to `concluida`, and Frases closing no longer raises a screen, because @/ui/pages/review is the next station and it is already reachable (until ENG-725 it announced `'segmentacao'`). Confirming any earlier scene returns `next-scene` and shows nothing. **The `'triagem'` boundary is unchanged**: the primary button just clears the state, revealing Frases (already mounted behind the screen); "Guardar e descansar" clears it AND calls `navigate('/dashboard')`, the same autosaved exit as the header's back pill. **A third value, `'historia'`, is raised by @/ui/pages/review itself** (its own "Concluir a história" action, `onBlockClosed('historia')`) when the story is concluded — this is the flow's actual end since ENG-725. There the primary ("Voltar às histórias") both clears the state and navigates to the dashboard, since there is no station left behind the screen to reveal; the secondary ("Olhar de novo") clears the state WITHOUT navigating, so the Review — still mounted behind, panorama intact — reappears. `onContinue`/`onRest` in @/ui/organisms/block-done/block-done.tsx branch on `closedBlock === 'historia'` vs `'triagem'` to pick the right destination for each block's two actions.
- **The block-done screen joins that same mechanism, and it does NOT get the sixth edge** (ENG-651). Five of the six directions are wired; `blockOpen` is deliberately absent from the block-done screen's own `busy`, so the celebration waits for it but it never waits for the celebration. Two reasons, and they agree. **The design source says so:** in @/docs/design/prototype.html both `pausaShow` (L1022) and `metaShow` (L1030) guard on `!blockDone`, while `blockDone` is assigned with no guard at all — a closed block outranks both. **And the symmetric version cannot work:** `open` in this screen and in the celebration are both DERIVED at render (`block !== null && !busy`, `reached && !busy && !dismissed`), so two derivations reading each other oscillate — both open in one render off the other's stale `false`, both close in the next, forever. That is not a theory: mutating the shell to add the edge makes React throw `Maximum update depth exceeded`, and `block-done-wiring.test.tsx` catches it. With the break there is no such risk, because its `open` is a latched state rather than a derivation, which is exactly why THAT direction is safe to make two-way.
- **"Defer, never swallow" matters more here than for its two siblings.** The break and the celebration re-evaluate continuously, so a threshold crossed under `busy` surfaces later on its own. A block closes exactly ONCE: if the screen were suppressed instead of deferred, there would be no second crossing to catch. What makes it safe is that the trigger and the render are separated — `closedBlock` is shell state that `busy` never touches, and only the rendering waits — so when `breakOpen` clears the screen appears on the next render.

- **Addons layer** (@/ui/app/addons-layer.tsx): a fixed bottom-right overlay region above the station, `pointer-events: none` except on the addons themselves — discreet chrome that never blocks the station. Its first occupant is the tutorial addon (@/ui/app/addons/tutorial.tsx): it reads the session from @/ui/state's `useSessionStore`, derives the current station via @/ui/app/stepper-model.ts (`stepperStations`, the entry whose state is `current`), and renders the @/ui/organisms/tutorial-popup organism keyed by that station; no session (login/dashboard) renders nothing. The popup deliberately renders inline (no Radix portal) so it stays inside `.cds-addons-layer` — never inside the station's `main`.

### Things to Know

- **`@/ui/app/resume-placement.ts` and its `reviewIsDone` are gone (ENG-689).** The question that module answered — "does a resumed session open on Export, or on the review it just finished?" — only existed because Export and its review could both be reached from a resumed interview-mode session. Neither exists any more: `stepper-model.ts`'s `currentIndex` maps the terminal domain mode straight to the Frases station (see Core Implementation), so a resumed session has exactly one place to open, and @/ui/app/App.tsx's `useSessionHydration` needs no placement logic to find it. **ENG-691 finished the job**: the `reviewComplete` argument `useSessionHydration` used to pass `false` for (there being no review left to describe) is gone from `toSessionDto`'s signature entirely, since @/contracts/session-state.ts dropped the field from the DTO — see the rehydration entry above and @/contracts/docs.md.

- **The shell is edited only for shell-held wiring, and rarely.** The add-a-file registries mean stations/adapters/addons normally land without touching this folder; the durable-shell promise is about registration, not immutability. The one-time exception this used to record — ENG-270 wiring `{ store, sessionId }` into the Export tail, since a completion/download page needed the shell-held sessions store and the route's session id — left with Export in ENG-689; every remaining station resolves everything it needs internally (session via `useSessionStore`) plus the uniform `stationProps` (see Core Implementation). The registries themselves stay static top-level `import.meta.glob` literals (a Vite requirement) wrapped in factories whose modules-map parameter defaults to the glob, so tests inject a fake map without touching disk; zero matches yields `{}`.
- **The app-global sessions store** (@/ui/app/session-adapter.ts, `appSessionStore()`, ENG-272/ENG-247): ONE lazily-memoized **mode-aware** singleton, the single source of session state for the whole facilitator flow — @/ui/pages/setup and @/ui/pages/dashboard resolve it (their `ports.ts` `defaultSessionStore()` returns it), so a session created in Setup appears in the Dashboard list. (@/ui/pages/export was a third resolver of this same singleton; it left in ENG-689.) Fixture (the default): a `FixtureSessionStore` over the shared `FixtureSessionBackend`, persisted to browser `localStorage` (resolved defensively, and falling back to memory-only when the stored blob is corrupt — the backend hydrates in its constructor, so bad JSON would otherwise crash the whole shell on every session route). Real: the `HttpSessionStore` (@/adapters/sessions/http.ts) wired with the browser connectivity monitor, the logged-in editor as a `user` thunk from `appAuth()`, an **async token that awaits `authReady()`** — every session call queues behind the boot resume, so a reload on `/session/:id` cannot race a 401 — and `onLockLost` → `setLock({ holder })`. That last hookup closes the fencing circuit (§7.3): a fire-and-forget autosave refused with SESSION_LOCKED is the only way the UI learns the session was taken, and only this wiring layer can make the connection (adapters never import ui).
- **The addons glob eats every direct-child `.tsx`**: `/ui/app/addons/*.tsx` eagerly imports ANY sibling `.tsx` as an addon component. Never place a non-addon `.tsx` directly in `ui/app/addons/` — addon tests live one level down in `ui/app/addons/__tests__/`, outside the one-level glob. The header comment in @/ui/app/addons-layer.tsx still says the directory starts empty in production; that predates the first addon — @/ui/app/registries.test.ts now asserts real glob discovery (the tutorial addon is found) instead of emptiness.
- **The theme boot script in @/index.html is duplicated on purpose, and the CSP knows it** (ENG-391). It repeats `theme.ts`'s precedence as a synchronous inline `<script>` in `<head>` because a React effect runs after the first paint and a dark-theme user would see a white flash on every load; importing the module would mean waiting for the bundle, which is the thing being avoided. Both files carry a comment pointing at the other. The catch a future reader will not expect: @/security-headers.conf ships `script-src 'self'` with **no** `'unsafe-inline'`, so the inline script only runs in production because its **sha256 hash** is listed there. Editing the script changes the hash; @/ui/app/theme-boot.test.ts recomputes it and fails, because otherwise nginx would silently block the script and the flash would come back in production only. Vite copies inline `<head>` scripts into `dist/index.html` byte for byte (verified on the built output), so the source hash is the shipped hash.
- **The favicon is index.html's other static-asset contract, and nothing at runtime checks it.** @/index.html declares `<link rel="icon" type="image/svg+xml" href="/favicon.svg">` pointing at @/public/favicon.svg; Vite serves `public/` at the site root and copies it into `dist/` unchanged because @/vite.config.ts sets no `publicDir` (the default applies). @/ui/app/favicon.test.ts is the only thing that reads both halves together — it parses the `<link>` out of `index.html` and asserts the file it points to exists in `public/`, because a dangling href degrades silently to the browser's blank default, with nothing at runtime or in the build to catch it. The icon is the site mark (@/docs/design/website-icon.svg → @/ui/tokens/icon.tsx's `ColarIcon`) redrawn for 16px rather than cropped, and hardcoded to literal hex values rather than tokens because a `public/` file never passes through the bundler; its own `prefers-color-scheme` media rule (inside the SVG) covers the dark tab strip the way `ColarIcon`'s `onDark` prop covers it in React.
- The player container invariant is load-bearing: never swap the portal container — move the persistent holder node instead, or the whole player subtree remounts (react#12247) and playback dies on every station change.
- **The session player is mode-aware** (@/ui/app/audio-player.ts, ENG-275/ENG-247): in real mode `buildSessionPlayer` decodes the bucket's actual audio bytes with the @/adapters/audio `WebAudioEngine` — the AudioContext clock drives itself, no bridge. In fixture mode the bucket serves `PcmSpec` JSON that only the `FixtureAudioEngine` decodes, and its transport clock only advances through the rAF→`advance` bridge (`startClockBridge`). Both paths fetch the audio through the mode-aware `appBucket()` (@/ui/app/bucket-adapter.ts).
- Navigation never bypasses the gates, and since ENG-668 there is no shell-level navigation at all: stations move the session themselves through `sessionStore.apply`, a no-op unless `canEdit()` (see @/ui/state/docs.md), so offline/review/lock still freeze station changes without losing state. **There is no one-way tail any more (ENG-689).** The Guardar (Export) tail this bullet used to describe — reachable only through the report's "Guardar os documentos →", with no station-level control leading back out — is gone along with Export itself; @/ui/pages/review is now the last station (ENG-725), and the flow's only "exit" is its "Concluir a história" action, which raises the end-of-flow block-done screen whose primary leads back to the dashboard.
- Online state has two sinks on purpose: the local flag renders @/ui/organisms/connection-gate immediately, and `sessionStore.setOnline` pauses mutations — both fed from the `connectivity` port subscription AND from window `online`/`offline` events (`useOnline` adds/removes both, cleaning up in the effect teardown). The window bridge is what lets Playwright's `context.setOffline` drive the gate + pause with no app/fixture change (ENG-277) — the "small dev/test connectivity hook" kept entirely in the composition root.
- **`GET /projects` sits outside the contracts surface on purpose.** @/ui/app/bucket-adapter.ts's `listAllProjectIds` (the platform-admin fallback in `resolveProjectId`) is the only caller and reads the response with an inline cast, not a @/contracts/api.ts zod schema — the same style already used there for the `/audios` probe. `GET /projects` is not under the `/api/auth/*`/`/api/sound-necklace/*` scope @/scripts/api-snapshot.mjs filters into @/contracts/openapi.json, so it can't be schema-checked against that snapshot; this is accepted debt, not an oversight, and stays scoped to this one fallback path.
- **The app-global auth singleton** (@/ui/app/auth-adapter.ts, `appAuth()`, ENG-277/ENG-247): ONE lazily-memoized **mode-aware** provider shared by Login, Dashboard (@/ui/pages/dashboard/ports.ts `defaultAuth()` delegates to it) and the session root's `useAuthExpiry`. Because all surfaces hold the SAME instance, a single expiry trigger (or the login's own token) is observed everywhere — expiring mid-Triage has someone to notify. Real mode mounts the `HttpAuthProvider` (@/adapters/api/client.ts: email login, roles via my-roles, rotating refresh persisted in localStorage — §12 as amended by owner decision; see @/adapters/api/docs.md). `authReady()` (same module) is the **single-flight boot resume**: anything token-dependent awaits it before reading `appAuth().token()` — the session store's async token getter and the bucket's project resolution queue behind it (a third queuer, the TTS 401 handler, left with @/adapters/tts in ENG-689), so a reload cannot fire 401s while the persisted refresh is still becoming a session. `useAuthGate` (@/ui/app/auth-gate.ts + `App`) completes the story: in real mode, once the resume settles with no user, any route but login redirects to `/login` instead of running silently unauthenticated; the fixture never gates (tests/dev need no login).
- **The shared fixture backend is exposed** (@/ui/app/session-adapter.ts, `appSessionBackend()`, ENG-277): the fixture branch of the app-global `appSessionStore()` is built over this lazily-memoized `FixtureSessionBackend` singleton, exported so a test can build a SECOND `FixtureSessionStore` over the SAME backend as a different user — the only way to seed a foreign advisory lock (two Playwright browser contexts have separate localStorage otherwise). The real mode does not touch it.
- **Dev-only resilience test seam** (@/ui/app/test-seam.ts + @/ui/app/main.tsx, ENG-277 → acceptance-6 ENG-257): `installTestSeam()` attaches `window.__cds` with `expireAuth()` (→ `appAuth().simulateExpiry()`) and `seedForeignLock(id, holder?)` (acquires the lock via a second store over `appSessionBackend()` as user "Ana"). These are the two resilience triggers with no natural UI/localStorage path; offline needs no seam (`context.setOffline`). @/ui/app/main.tsx imports and installs it lazily ONLY under `import.meta.env.DEV`, so it never ships in the production bundle — the E2E webServer runs Vite dev, where DEV is true.
- **Shell copy now routes entirely through the dictionary** (ENG-279, @/ui/i18n/docs.md): the header, the review/lock banner (@/ui/app/review-banner.tsx) and the "estação em construção" fallback (@/ui/app/station-host.tsx) call `t()` directly. The station labels stay data: @/ui/app/stepper-model.ts is i18n-free and emits a `labelKey` per station, which @/ui/app/story-progress.tsx resolves with `t(labelKey)` — the model is derived from domain gates, so keeping copy out of it is what lets it stay a pure function. @/ui/pages/dashboard keeps its OWN copy of the station-label keys (a separate array, since its step names differ from the stepper's) but reads the SAME `stations.*` translations, so the stepper can read PT while the dashboard glance reads EN. The one copy that still renders PT-BR under an EN UI is emitted by @/domain/@/contracts themselves (gate/error messages) — translating those is a frozen-layer change, out of scope for `ui/`.
