# Noridoc: ui/app

Path: @/ui/app

### Overview

- The composition root and wiring layer of the Shemá app (ENG-224): the only place that imports adapters, @/domain, @/ui/state and @/ui/organisms together. It is the durable shell — station/adapter/addon issues almost always land purely by ADDING files under @/ui/pages, @/adapters or `ui/app/addons`. Rare, deliberate one-time exceptions wire a page that needs shell-held ports (ENG-270 made the Export tail reachable and injects the sessions store + sessionId — see Things to Know).
- Owns the app frame (@/ui/app/header.tsx brand + sound toggle), the whole-story progress bar (@/ui/app/story-progress.tsx, ENG-648) and the "fio de contas" progress stepper, the single itinerant player (now with a live audio `Player` built per-session, ENG-275), review/lock chrome, the online-only connection gate, and the station host — all mounted from @/ui/app/App.tsx. It also wires the three resilience seams into the running session view (ENG-277): offline (window `online`/`offline` events), mid-session auth expiry (→ `/login`), and an advisory lock held by another editor (→ review chrome).
- The chrome was realigned to `docs/design/Colar de Sons - Protótipo.dc.html` (CLAUDE.md precedence rule 2), then extended by the v4 prototype — `docs/design/prototype.html` since ENG-647 landed it; every "v4 prototype, line N" below is a line of THAT file (ENG-648): a 64px icon-only header with a "← Histórias" pill, a 46px band carrying the current station's NAME above the whole-story progress bar, and a 28px row of stepper dots below it. All three are documented in detail below. The station name lives in the progress band now, NOT in the stepper — it used to be rendered above the dots, and keeping it there would print it twice, one line under the other.
- App entry chain: @/index.html → @/ui/app/main.tsx (loads the token side-effects once, and imports @/ui/i18n for its init side effect **before the first render** — without that import every screen renders raw translation keys) → @/ui/app/App.tsx.

### How it fits into the larger codebase

- Outermost wiring layer of the atomic-design ladder documented in @/ui/docs.md. Per @/.dependency-cruiser.cjs it may import everything (adapters, domain, state, organisms); atoms/molecules/organisms below it may not reach back up.
- **Owns the three add-a-file registries** (@/docs/architecture.md §4), created once in @/ui/app/registries.ts and never edited again:

  | Registry | Glob                      | Builder                | Keyed by       |
  | -------- | ------------------------- | ---------------------- | -------------- |
  | Stations | `/ui/pages/*/index.tsx`   | `buildStationRegistry` | directory name |
  | Adapters | `/adapters/*/register.ts` | `buildAdapterRegistry` | port name      |
  | Addons   | `/ui/app/addons/*.tsx`    | `listAddons`           | sorted by path |

  This is the loop's no-file-conflict guarantee: landing a station, adapter, or overlay = adding files, never touching a shared registry. The pattern is proven: the first addon (@/ui/app/addons/tutorial.tsx, the tutorial popup, ENG-231) landed without editing a single shell file.

- Reads domain decisions through @/ui/state stores (never mutating @/domain directly): `useSessionStore`/`useAppStore` supply session state, the review/lock/online gate flags, and the sound toggle. Stepper navigation dispatches `setMode` through `sessionStore.apply` so the domain gates decide whether the move is allowed.
- Subscribes the `connectivity` adapter port (fixture default, @/adapters/connectivity) and mirrors online state both into a local flag for @/ui/organisms/connection-gate and into the session store, which pauses editing when offline.

```
index.html → main.tsx → App.tsx (composition root)
   ├─ Header (brand + sound toggle → appStore)
   ├─ StoryProgress (station name + whole-story bar, story-progress-model)
   ├─ Stepper (fio de contas, stepper-model ← domain modeLocks)
   ├─ ReviewBanner (review/lock chrome ← sessionStore)
   ├─ PlayerSlotProvider (the one traveling player)
   │    └─ ConnectionGate (online) → StationHost → ui/pages station
   ├─ BreakSuggestion (a pausa sugerida, session view only)
   ├─ GoalReached (a meta de hoje alcançada, session view only)
   ├─ BlockDone (o fim de bloco, session view only)
   └─ AddonsLayer (ui/app/addons overlay chrome)
```

### Core Implementation

- **Router** (@/ui/app/router.tsx): a minimal History-API router — react-router is out of scope. `matchRoute` resolves `/login`, `/dashboard` (also `/`), `/setup`, `/session/:id`, else `unknown`. `navigate()` calls `pushState`/`replaceState` and then notifies subscribers by hand, because pushState never fires `popstate`; `subscribe` additionally listens for `popstate` (browser back/forward). `usePathname`/`useRoute` read through `useSyncExternalStore` with `location.pathname` as the snapshot (a primitive, so `Object.is` comparison is stable).
- **The real-mode switch** (@/ui/app/api-config.ts, ENG-247): `VITE_API_MODE`/`VITE_API_BASE_URL` are read ONCE here by the composition root — adapters never read env, they receive baseUrl/token injected. Every app-global singleton keys off `API_MODE`: auth (@/ui/app/auth-adapter.ts), sessions (@/ui/app/session-adapter.ts), bucket (@/ui/app/bucket-adapter.ts — which also resolves the facilitator's project via `my-project-roles`, caches it for the tab, and for multi-project accounts keeps the first project that actually has bucket audio; a platform admin gets an empty `project_roles` back for the same reason `my-roles` is empty for them — see @/adapters/api/docs.md — so `resolveProjectId` falls back to `listAllProjectIds()` over `GET /projects` before the same audio probe runs), the per-session voice store (@/ui/app/voice-adapter.ts) and the session audio engine (@/ui/app/audio-player.ts). Fixture remains the default, keeping tests/CI networkless.
- **The itinerant player** (@/ui/app/player-slot.tsx, PRD §8.0 / redesign §5.2): there is ONE player instance that travels to the active station's slot. Because changing a `createPortal` container remounts the subtree (react#12247), the player node lives in a persistent detached `holder` div (lazy `useState` init) that the portal always targets; the holder is MOVED between `PlayerHost` slots via `appendChild` (append moves, does not clone) in a `useLayoutEffect`. Placement runs through refs (no `setState` during commit), so a late-mounting lazy station host still receives the player. On active-station change it calls `player.stop()` — fed `player ?? NO_PLAYBACK` (a module-level no-op `{ stop() {} }`) so navigating between stations still stops audio, mirroring the reference `setMode`→`stopPlayback`.
- **The session audio player** (@/ui/app/audio-player.ts + @/ui/app/App.tsx `useSessionPlayer`, ENG-275/ENG-247, PRD §8.2): the composition root builds the actual audio `Player` for the active session and threads it to the necklace station (this is the audio analog of ENG-270's Export reachability). `buildSessionPlayer(sessionId)` re-decodes the session's bucket audio (`meta.bucketAudioId` from the persisted DTO via `appSessionStore().load`, bytes fetched through the mode-aware `appBucket()`), builds the `Player` with the session's locked `beadSec` on the engine the mode dictates — real: @/adapters/audio `WebAudioEngine`, whose AudioContext clock drives itself; fixture: `FixtureAudioEngine` plus the clock bridge — and rejects if the session has no saved state or the bucket audio does not resolve. `startClockBridge(transport)` (fixture-only need) drives the `FixtureTransport` — whose clock only advances on `advance()` — from `requestAnimationFrame` using the real inter-frame delta, so playback progress + `onHead` (and thus the necklace `data-play` playhead) advance in the running browser (Playwright ticks rAF); it returns a canceller. `useSessionPlayer` rebuilds on session change and, on cleanup, stops the player + cancels the bridge; a session whose audio can't resolve degrades to a dormant `null` player (stations already handle `player = null`).
- **The fio-de-contas stepper** (@/ui/app/stepper-model.ts + @/ui/app/stepper.tsx): `stepperStations` derives the six station states (Ouvir · Cortar · Triage · Frases · Conversa · Guardar) from domain `modeLocks()` (@/domain) plus mode/flow position. `reachable` mirrors the gates; `state` is done/current/future by flow index. The Guardar (export) tail has no domain mode — the domain `Mode` is only escuta|triage|phrases|conversation — so its `reachable` equals the Conversa/conversation gate (`modeLocks().conversation`: whole story confirmed + ≥1 locked phrase in a productive scene), and entering it is a shell-local concern: the optional `{ viewingExport }` option marks Guardar as `current` (earlier beads as `done`) without any domain mode change. It is a progress indicator, not free navigation — the `<ol>` uses one delegated click handler mapped by `<li>` index, and only navigates to `reachable` stations. Zero digits render (PRD §9.2); the station `key` doubles as the @/ui/pages directory name the station registry resolves.
- **Stepper visuals realigned to the Protótipo** (`ui.wizardStyle`): the `<ol>` carries the full accessible name via `aria-label`, so screen readers never lose the station names. The visible station name is a sighted-only echo and, since ENG-648, it is rendered by @/ui/app/story-progress.tsx one band above; the stepper band is therefore dots-only and 28px tall (it was 46px when it also held the name). @/ui/molecules/stepper-station renders each dot at 11px (current, with a halo) or 7px (done/future), replacing the previous 20px/13px "lit vs head" pearl-state distinction — the current dot uses `state='lit'` (a color, not the playhead ring) and gets its emphasis from size + halo in CSS instead.
- **The whole-story progress bar** (@/ui/app/story-progress-model.ts + @/ui/app/story-progress.tsx + @/ui/molecules/story-progress-bar, ENG-648, v4 prototype lines 269-277/1644-1668): one thin bar under the header showing how far the WHOLE story has come — not how far the current station has come. The band is 46px: the current station's name (`aria-hidden`, uppercase, from the same `stations.*` keys the stepper model emits) above a 480px/56vw track carrying the fill, five stage dividers, a marker and — since ENG-653 — the goal mark. The progress half of `storyBarValues` weights the six stations `[8, 14, 12, 26, 32, 8]` (summing to 100, so the dividers sit at 8/22/34/60/92) and adds the current station's weight × its own completion fraction: heard beads ÷ total beads (Ouvir), scenes ÷ 5 (Cortar), non-`pending` scenes ÷ scenes (Triagem), productive scenes with ≥1 phrase ÷ productive scenes (Frases), `lastAnsweredIndex + 1` ÷ `questionSequence.length - 1` (Conversa), artifacts downloaded ÷ 3 (Guardar). Completed stations count their full weight, so the bar never walks backwards on a station change. **Every one of those is a division and several denominators are zero in a real session** (no scenes, no productive scenes) — the module has exactly two division gates, `ratio()` for progress (returns 0 for a non-positive denominator) and `share()` for the goal (floors the denominator at 1), and `StoryProgressBar` clamps again before the value reaches a CSS `width`, because a `NaN` there is not an error, it is a bar that silently does not render. The arithmetic sits in `ui/app` for the same reason `stepper-model.ts` does: it is view derivation over `SessionState`, and the shell is the only layer that sees both the domain state and the view-local facts (being in the Guardar tail, how much was heard, how many artifacts were saved). It is NOT domain — the weights are a design choice, not a PRD rule, and nothing here reaches an artifact.
- **Two of the six fractions cannot be read from `SessionState`** and arrive through @/ui/state's `progressStore` (ENG-648): how much of the story has actually been HEARD (@/ui/pages/listen publishes the size of its cumulative heard-bead set on every new bead) and how many artifacts have been DOWNLOADED (@/ui/pages/export publishes the count whenever its `downloaded` map changes). Neither is a domain decision and neither enters an artifact, so neither belongs in the session DTO. `StoryProgress` subscribes to that store ITSELF rather than taking the numbers as props: Escuta 1 publishes on every new bead during playback, and subscribing in `SessionStations` would re-render the whole open session — station, player provider and all — several times a second. `SessionStations` resets the store on mount (it is remounted by `key={sessionId}`), so one session's progress never opens the next one already advanced.
- **Review/lock chrome** (@/ui/app/review-banner.tsx, PRD §8.10 / §7.3): renders the review banner and "Destravar para editar" when in review with no foreign lock; when another editor holds the advisory lock it shows "sessão em uso por <name>" and offers no unlock (the lock forces review). A lock with no holder name (`{ holder: null }`, @/ui/state/docs.md) renders a distinct "reconnecting…" message instead — @/ui/app/use-editor-lock.ts's renew deadline expired without an answer, or a 409 SESSION_LOCKED arrived without a `holder_name`. State comes from the session store.
- **Non-session route → station resolution** (@/ui/app/App.tsx): `login`/`dashboard`/`setup` resolve the same-named station; an `unknown` top-level path resolves the station named by its first path segment (so `/imports`, whose station lands in ENG-248, renders once its folder exists) and otherwise falls through to the station host's "em construção" placeholder. This is what makes `/setup` reachable now that the router matches it — the dashboard's "Comece uma nova história" card navigates there and lands on the Setup station.
- **Session rehydration + continuous autosave** (@/ui/app/App.tsx `useSessionHydration`, PRD §7.3): on `/session/:id` with an empty in-memory @/ui/state (a browser reload or a resume-from-dashboard, where Setup never populated the live store), it `load`s the persisted DTO from the app-global store and injects `fromSessionDto(dto).state` into `sessionStore`, so the session resumes at its current step instead of stranding on "carregando a sessão…". A `loadedId` ref guards against reloading over a live session (Setup already loaded the freshly-created one) and re-runs when the route id changes. In the same step it **wires the autosave port** (ENG-273): `sessionStore.setAutosave(live => appSessionStore().autosave(routeId, toSessionDto(live, meta, reviewIsDone(live, meta.voice))))`, so from then on every domain mutation persists the WHOLE state under this session's `meta` (granularity/audio/consent, captured from the loaded DTO) — without this, only Setup's initial DTO and completion were ever written, and a reload resumed on Escuta 1 losing all decisions. `useAutosaveFlush(routeId)` flushes the adapter's debounced queue on `pagehide` (reload/close) and on session change, closing the debounce window so the last decision is never lost. The same hook decides **where the resumed session opens**, and the shell shows the waiting stage until it knows (ENG-511): it returns `{ ready, initialExport }`, and @/ui/app/App.tsx mounts no station while `ready` is false. That gate is not cosmetic — @/ui/state is NOT cleared between sessions, so mounting immediately rendered the PREVIOUS session's station, review cards and all, under the new session's route until hydration landed. A load that FAILS settles too, with no Export: a read error must never become "go to Guardar". Voice answers register their canonical path into `meta.voice` through `onVoiceSaved`, which autosaves AND flushes immediately (ENG-276) — recording is a discrete action and entering Export triggers no flush, so waiting out the debounce could ship a report with "sem resposta". Both write paths recompute `reviewIsDone(live, meta.voice)` for the DTO's `reviewComplete` flag (ENG-514) rather than carrying one forward — recording an answer that has no confirmed text yet takes a session that was reporting `save` back to `conversation`, which only holds because the flag is derived at every write.
- **The lock has ONE owner** (@/ui/app/use-editor-lock.ts, ENG-299 / ENG-247, PRD §7.3): `App` mounts `useEditorLock(routeId)` on session routes, in BOTH modes (the fixture serves locks too — one code path, not two). It is the acquire → heartbeat → release side of the tripod-api lease (ENG-262: `PUT /sessions/{id}/lock` acquires AND renews, 60s TTL). Acquiring against a foreign holder opens review (`setLock({ holder: <name> })`, the "sessão em uso por" banner); otherwise it renews every `HEARTBEAT_MS` (15s) with +0–20% jitter — deliberately NOT client-go's `JitterFactor` of 1.2, which multiplies a 2s retry period; applied to a 15s heartbeat that would allow beats up to 33s and blow the 60s TTL after two misses. A renewal that comes back held by someone else (or by nobody) demotes immediately, without waiting for a write to be refused. A separate `RENEW_DEADLINE_MS` (45s) is re-armed only by a SUCCESSFUL renewal; if it fires, the client demotes ITSELF to review (`setLock({ holder: null })`) without waiting for a 409 — that is what actually closes the two-editor window, since nobody else can take the lease before the 60s TTL anyway. A FAILED acquire (network, transient 5xx) is not final either (ENG-338): it parks the session in review with the reconnection banner and then retries while the route stays mounted, waiting `ACQUIRE_RETRY_MS` (2s) and doubling up to `ACQUIRE_MAX_RETRY_MS` (30s) — the same recursive-`setTimeout` backoff @/ui/pages/report/use-stt-drafts.ts uses, and never a `setInterval`, which would pile attempts up on a slow network. The first success promotes exactly like a fresh acquire, heartbeat and deadline included. A foreign holder is NOT retried — that is not a failure, it is the session being in use. Release fires on unmount and on `pagehide` (best-effort — a DELETE fired as the page unloads is usually cut off; the 60s TTL is what actually reclaims a closed tab, `pagehide` only speeds up the common in-SPA case of switching sessions). `useSessionHydration` consequently does NOT touch the lock anymore — it only resets `setReview(false)` per (re)hydration so one session's review flag cannot leak into the next in-SPA; the one-shot `lockStatus` read that used to live there was removed when this hook was wired, because both wrote the same `setLock`/`setReview` and would race. The second half of the circuit is `onLockLost` in @/ui/app/session-adapter.ts: an autosave refused with 409 SESSION_LOCKED calls `setLock({ holder })` with the usurper's name from the response body.
- **Mid-session auth expiry** (@/ui/app/App.tsx `useAuthExpiry`, ENG-277, PRD §7.1): subscribes the app-global `appAuth().onAuthExpired(() => navigate('/login'))`, so a server token expiring on ANY route — `/session/:id` included — routes back to login WITHOUT touching the in-memory session state (re-login resumes at the same step). Previously this was wired only in the dashboard page, so expiring mid-session did nothing.
- **Station host** (@/ui/app/station-host.tsx): resolves the active station from the registry; a not-yet-built station falls back to a quiet "estação em construção" line, so a station issue enters purely by adding its `ui/pages/<station>/` folder. It accepts optional `stationProps` and forwards them to the resolved component: most stations resolve everything internally (session via `useSessionStore`) and take no props, while stations needing shell-held wiring ports receive them here. Prop-less stations ignore unknown props. @/ui/app/App.tsx passes `{ store, sessionId }` when the Export station is current — `store` is the app-global sessions adapter (@/ui/app/session-adapter.ts), `sessionId` comes from the `/session/:id` route — `{ recorder, player }` when the Conversation station is current (the `voice` recorder rebuilt per session from the direct @/adapters/voice/register import, injected with the per-session answer store `voiceStoreFor(routeId)` from @/ui/app/voice-adapter.ts — in real mode that is a `SessionVoiceStore` over the session's server-side resources, so a reload re-finds the recordings; **`real()` by default, so the interview mic actually records §8.7**; `fixture()` only under `VITE_VOICE=fixture`, which is set for the jsdom project (no MediaRecorder there) and by nothing else. The e2e deliberately does NOT set it: Chromium supplies a fake mic (`--use-fake-device-for-media-capture`) so `tests/e2e/voice-really-records.spec.ts` can weigh the recorded blob and fail if the dummy ever comes back — the app shipped mute for a week behind a fixture whose level meter moved (ENG-298), and a path-only assertion could not see it. Plus the audio `Player` to play the phrases, and — since ENG-327 — the `stt` transcriber and the `sessionId`, which Conversation only forwards to the report station; and — since ENG-649's overlay wiring — `overlayBusy` (`breakOpen || goalOpen || blockOpen`, so the mode picker never covers one of the other three) and `onModePickerChange` (`setModePickerOpen`, so the other three can hold off while the picker is up in return — see the overlay precedence entries below), and `{ player }` to the other necklace stations (listen/cut/triage/phrases) so they play beads/edges/scenes (§8.2, ENG-275). The `player` is the `Player | null` from `useSessionPlayer`; stations already handle `null`. The in-session body lives in a `SessionStations` child that holds the local `viewingExport` flag: clicking the reachable Guardar bead sets it true (landing on Export); navigating any other station clears it and dispatches `setMode` as before. Until the first navigation click, the view follows `initialExport` from the hydration — a completed session reopens on Export (ENG-320) and so does one whose review is already fully confirmed (`reviewIsDone`, @/ui/app/resume-placement.ts, ENG-511); the first click takes over and hydration never pulls it back. That child is remounted via `key={sessionId}`, so switching sessions resets `viewingExport` — without the remount the flag would leak and a session that never reached the gate would open on Export (the reset avoids `set-state-in-effect`/`set-state-in-render`, both lint errors here). It is also where the session's net-time clock pulses (`useSessionClock`, @/ui/state/session-clock.ts): the shell is the only place that knows which session is open, and the Export reads the frozen total when the session completes.
- **Header** (@/ui/app/header.tsx, realigned to the Protótipo's 64px band): icon-only left side — a "← Histórias" pill (`onBack`, wired to `navigate('/dashboard')` in @/ui/app/App.tsx) plus a bare `ColarIcon` (the site mark; it replaced the `ShemaIcon` that used to be painted wholesale from `--cds-chrome-mark` — a multi-colour drawing cannot take a single fill, so `header.css` now repaints only its cord and end beads, from `--cds-chrome-fg`, which is olive on a light station, cream on the ceremonial olive ones, and body-ink under the dark theme), no eyebrow/title/subtitle text (those were removed; the app name now lives only on the Dashboard). The right side keeps the sound toggle (`aria-pressed`, flips `appStore.muted`; as of today nothing else reads that flag) and, since ENG-391, the light/dark theme button beside it (moon in light, sun in dark; the accessible name states the destination, not the state). The theme button is prop-driven exactly like the sound one — `theme` + `onToggleTheme` come from @/ui/app/App.tsx — and it renders ONLY when `onToggleTheme` is supplied, so `Header` never shows a control that does nothing. Both are v2-only chrome with no golden-harness constraint. **The language toggle used to live here and was removed in ENG-371:** a one-click PT/EN switch beside the sound control invited flipping mid-session, and the UI language governs the interview voice and the locale sent to STT. The choice now lives in @/ui/pages/settings, beside the project's granularity. **ENG-375 then removed the Settings entry from this header too:** the header is mounted on every station, so an entry here was reachable mid-session and undid the very friction ENG-371 created. The only way in is the gear on the Dashboard — which replaced that screen's own copy of the language toggle. **It is NOT mounted on every route:** `ownsHeader` (@/ui/app/App.tsx) suppresses it on `login` and `dashboard` (ENG-278) — both are full-bleed surfaces that ship their own header. Those two routes consequently have no sound/back toggle: they are facilitator surfaces with no playback, while every station keeps it.
- **Dark chrome variant is CSS-only, no prop-drilling** (@/ui/app/app.css): the header, the progress band and the stepper read chrome colors from `--cds-chrome-*` custom properties set on `.cds-app`. `.cds-app:has(.cds-listen)` and `.cds-app:has(.cds-conversation-stage)` override those properties to the dark (cream-on-olive) palette; every other station falls through to the light default. The progress bar's own two shades ride along as `--cds-chrome-progress-track`/`--cds-chrome-progress-line`, defined in all three variants; its fill and marker halo reuse `--cds-chrome-accent`, and the marker itself is cream in BOTH themes (the v4 prototype pins it), so it is the one hardcoded colour in the molecule. Because the selector keys off the STATION'S OWN root class being present in the DOM, the Conversation report preview (@/ui/pages/report) automatically returns the chrome to light the moment `.cds-conversation-stage` leaves the tree — no station needs to notify the shell of its "ceremonial" status.
- **Light/dark theme** (@/ui/app/theme.ts + @/index.html + @/ui/tokens/tokens.css, ENG-391): the theme lives in a `data-cds-theme` attribute on `<html>`, not in React state — `App`'s `useTheme` keeps a copy only so the header knows which glyph to draw. Precedence is stored explicit choice → `matchMedia('(prefers-color-scheme: dark)')` → light, and `initTheme()` deliberately **never writes**: persisting on boot would freeze a user who never chose to whatever the OS said the first time. `readTheme()` reads the attribute before falling back to that precedence, which is what keeps the toggle working in a window where `localStorage` throws (locked private window, exceeded quota — every storage access is wrapped). What actually repaints is the `--cds-ui-*` semantic role layer in @/ui/tokens/tokens.css; the brand and scale tokens above it are identical in both themes. **This issue shipped the plumbing only — component stylesheets still read the brand tokens directly, so switching to dark today changes native scrollbars/form controls (via `color-scheme`) and little else until the migration pass lands.**
- **Today's goal, and the mark on the bar** (ENG-653, v4 prototype lines 343-349/870-883/1030/1372-1379): the facilitator picks on Setup how far the pair mean to get today; `storyBarValues` turns that pick into a percentage on the SAME 0-100 track, and `StoryProgress` hands it to the bar as a fixed mark. The percentage is recomputed **every render** by design — the scene and question counts grow as the work goes on, so "2 cenas" walks left as scenes appear. That is also the performance trap ENG-648 fell into, so the model has ONE entry point: `storyBarValues(input, goal)` computes progress and goal together and does the expensive `questionSequence` walk lazily, at most once per call (and not at all when neither the current station nor the goal needs it). The anchors are derived, not copied: `STAGE_BOUNDARIES[2]`/`[3]` (34/60) are the ends of Triagem and Frases and `STATION_WEIGHTS[3]`/`[4]` (26/32) their band widths, so mark and fill cannot drift into different coordinate systems. `sceneCount` falls back to 4 when the session has no scenes and is floored at 1 — without the fallback `2/0` saturates at 1 and "2 cenas" would land exactly on "fechar as Frases", two different goals on one mark, with no `NaN` anywhere to give it away.
- **Who notices the goal was reached** (ENG-653): `StoryProgress`, because it is the one place both numbers meet. It reports the STATE (not an event) through `onGoalReached: (reached: boolean) => void`, so the shell can pass a `useState` setter directly — stable identity with no `useCallback`, which is what lets the React Compiler keep memoizing the band. The comparison carries the prototype's `- 0.01` slack, since the two sides come from different roundings.
- **One full-screen surface at a time, in BOTH directions — four surfaces now** (ENG-653, joined by the conversation mode picker in ENG-649's second half). `SessionStations` holds `goalReached` (from the bar) plus `goalOpen`, `breakOpen`, `blockOpen` and `modePickerOpen` (each organism/screen reports its own open state through `onOpenChange`, or — for the picker, which is a page-owned modal rather than an organism with that prop — through `onModePickerChange`) — and crosses them: the break gets `busy={recording || goalOpen || blockOpen || modePickerOpen}`, the celebration `busy={recording || breakOpen || blockOpen || modePickerOpen}`, the block-done screen keeps `busy={recording || breakOpen}` unchanged (see the precedence note below for why it is short by two terms, not one), and the picker gets `overlayBusy={breakOpen || goalOpen || blockOpen}` passed into @/ui/pages/conversation's `Conversation`, which derives `askingMode = mode === null && !overlayBusy` the same way the other three derive their own `open`. This EXTENDS the `busy` prop ENG-650 already had rather than adding a second scheme; the mechanism stays the `onOpenChange`-style callback that makes an exclusion symmetric, since a self-latching organism — or a modal owned by a page, in the picker's case — is otherwise invisible to the shell. All four treat `busy`/`overlayBusy` as "defer, do not swallow": a goal crossed mid-recording opens as soon as the mic closes, and the same is true of the picker crossed mid-overlay.
- **The suggested break** (ENG-650): `SessionStations` mounts @/ui/organisms/break-suggestion, the once-per-session rest suggestion (PRD-redesign prototype "PAUSA SUGERIDA"). The shell supplies exactly two things — `busy`, read from `useAppStore((s) => s.recording)` (the same app-global mic flag that disables the header's "← Histórias", ENG-393), and `onTakeBreak`, which is `navigate('/dashboard')`: the identical exit the header back pill uses, so the session is autosaved and resumable either way. Placement carries three of the four "never interrupt" guards for free: mounted INSIDE `SessionStations`, it does not exist on the waiting screen (which replaces that subtree wholesale), it does not exist outside a session, and the `key={sessionId}` remount re-arms the one-shot latch whenever a session is started, resumed or reopened for review. The threshold, the latch and the settle window all live in the organism; the shell holds no timer.

- **The end of a block of work** (ENG-651): `SessionStations` also mounts @/ui/organisms/block-done, the screen that marks a structural boundary. The shell holds the whole trigger, in one `useState<ClosedBlock | null>`, and that placement IS the feature: the station that confirms is precisely the one leaving the screen, so it cannot hold the state; and a session reopened past a boundary mounts this `null`, so the screen never replays on resume, on remount or on a re-render (`key={route.id}` on `SessionStations` is what makes it die with the session and only with the session). The two triggers are handed up by the stations through one `onBlockClosed` prop in `stationProps`, and **both read the answer from @/domain rather than re-deriving it in the UI**: @/ui/pages/triage announces `'triagem'` only when `setMode` actually moved the session to `segmentacao`, and @/ui/pages/phrases announces `'segmentacao'` only when `confirmFrasesDone` returns `kind: 'mapeamento'` — the domain's own name for "that was the last productive scene". Confirming any earlier scene returns `next-scene` and shows nothing. The primary button just clears the state, revealing the station that was already mounted behind it; "Guardar e descansar" clears it and `navigate('/dashboard')`, the same autosaved exit as the header's back pill.
- **The block-done screen joins that same mechanism, and it does NOT get the sixth edge** (ENG-651). Five of the six directions are wired; `blockOpen` is deliberately absent from the block-done screen's own `busy`, so the celebration waits for it but it never waits for the celebration. Two reasons, and they agree. **The design source says so:** in @/docs/design/prototype.html both `pausaShow` (L1022) and `metaShow` (L1030) guard on `!blockDone`, while `blockDone` is assigned with no guard at all — a closed block outranks both. **And the symmetric version cannot work:** `open` in this screen and in the celebration are both DERIVED at render (`block !== null && !busy`, `reached && !busy && !dismissed`), so two derivations reading each other oscillate — both open in one render off the other's stale `false`, both close in the next, forever. That is not a theory: mutating the shell to add the edge makes React throw `Maximum update depth exceeded`, and `block-done-wiring.test.tsx` catches it. With the break there is no such risk, because its `open` is a latched state rather than a derivation, which is exactly why THAT direction is safe to make two-way.
- **The mode picker collides with block-done on the NORMAL path, not an edge case** (ENG-649 second half). Closing the segmentation block moves the session to `mapeamento` in the same act that sets `closedBlock`, so BlockDone and the conversation mode picker were BOTH asked to open on the very first entry into the conversation, every time a pair finishes phrasing — not a rare race, the ordinary way into this station. Before this wiring the picker won the z-order and covered BlockDone's only exit, so the e2e helper `finishPhrases` (@/tests/e2e) hung on "Começar a conversa" every run. The picker yields to BlockDone the same way GoalReached already does — one-way: `overlayBusy` (fed to the picker) includes `blockOpen`, but BlockDone's own `busy` does not include `modePickerOpen` — and for the same reason: BlockDone speaks about the work that just ENDED, the picker about what is about to begin, so the picker waits its turn. BreakSuggestion and GoalReached wait for the picker instead (two-way), because unlike BlockDone's single deterministic trigger, either can fire at any moment mid-interview, and the picker — a gate the interview cannot proceed past — has no safe way to defer itself once it decides to open. The original ENG-649 issue already asked for exactly this ("never [ask] while a wait or a block-closing screen is up"); none of the three shell overlays existed yet when that branch started, which is why the wiring landed as a follow-up inside the same issue instead of at first cut.
- **"Defer, never swallow" matters more here than for its two siblings.** The break and the celebration re-evaluate continuously, so a threshold crossed under `busy` surfaces later on its own. A block closes exactly ONCE: if the screen were suppressed instead of deferred, there would be no second crossing to catch. What makes it safe is that the trigger and the render are separated — `closedBlock` is shell state that `busy` never touches, and only the rendering waits — so when the mic closes the screen appears on the next render.

- **Addons layer** (@/ui/app/addons-layer.tsx): a fixed bottom-right overlay region above the station, `pointer-events: none` except on the addons themselves — discreet chrome that never blocks the station. Its first occupant is the tutorial addon (@/ui/app/addons/tutorial.tsx): it reads the session from @/ui/state's `useSessionStore`, derives the current station via @/ui/app/stepper-model.ts (`stepperStations`, the entry whose state is `current`), and renders the @/ui/organisms/tutorial-popup organism keyed by that station; no session (login/dashboard) renders nothing. The popup deliberately renders inline (no Radix portal) so it stays inside `.cds-addons-layer` — never inside the station's `main`.

### Things to Know

- **Where a resumed session opens is computed, not stored** (@/ui/app/resume-placement.ts, ENG-511). The saved domain mode stops answering the question once the interview ends: the mode stays `mapeamento`, the Conversation sees nothing left to ask and opens the review, and a review that is entirely confirmed leaves no durable mark saying so — reopening dropped the facilitator back into the review they had just finished. `reviewIsDone(state, meta.voice)` answers it from the state hydration already holds, with two conditions and no rule of its own: the interview reached its end (`lastAnsweredIndex`, @/ui/pages/conversation/answered.ts — the same rule that makes the Conversation open the review, so the two cannot drift) and nothing is pending (`reportExportStatus`, @/contracts — the same number the Export gate refuses on). Nothing new travels on the wire: no DTO field, no server change, and the dashboard still loads no session state. **The mechanism first suspected was wrong and is worth recording:** the summary does NOT arrive after the state — `useSessionHydration` awaits `Promise.all([load, get])`, so on a reload the status and the state land in the same React batch and there is no window at all. The window comes from @/ui/state surviving the route change (see the rehydration entry above).

- **The shell is edited only for shell-held wiring, and rarely.** The add-a-file registries mean stations/adapters/addons normally land without touching this folder; the durable-shell promise is about registration, not immutability. The exception is wiring a page that cannot resolve everything internally: ENG-270 made the Export tail reachable and injects `{ store, sessionId }` into it, since a completion/download page needs the shell-held sessions store and the route's session id. The registries themselves stay static top-level `import.meta.glob` literals (a Vite requirement) wrapped in factories whose modules-map parameter defaults to the glob, so tests inject a fake map without touching disk; zero matches yields `{}`.
- **The app-global sessions store** (@/ui/app/session-adapter.ts, `appSessionStore()`, ENG-272/ENG-247): ONE lazily-memoized **mode-aware** singleton, the single source of session state for the whole facilitator flow — @/ui/pages/setup, @/ui/pages/dashboard and @/ui/pages/export all resolve it (their `ports.ts` `defaultSessionStore()` returns it), so a session created in Setup appears in the Dashboard list and is readable by Export. Fixture (the default): a `FixtureSessionStore` over the shared `FixtureSessionBackend`, persisted to browser `localStorage` (resolved defensively, and falling back to memory-only when the stored blob is corrupt — the backend hydrates in its constructor, so bad JSON would otherwise crash the whole shell on every session route). Real: the `HttpSessionStore` (@/adapters/sessions/http.ts) wired with the browser connectivity monitor, the logged-in editor as a `user` thunk from `appAuth()`, an **async token that awaits `authReady()`** — every session call queues behind the boot resume, so a reload on `/session/:id` cannot race a 401 — and `onLockLost` → `setLock({ holder })`. That last hookup closes the fencing circuit (§7.3): a fire-and-forget autosave refused with SESSION_LOCKED is the only way the UI learns the session was taken, and only this wiring layer can make the connection (adapters never import ui).
- **The addons glob eats every direct-child `.tsx`**: `/ui/app/addons/*.tsx` eagerly imports ANY sibling `.tsx` as an addon component. Never place a non-addon `.tsx` directly in `ui/app/addons/` — addon tests live one level down in `ui/app/addons/__tests__/`, outside the one-level glob. The header comment in @/ui/app/addons-layer.tsx still says the directory starts empty in production; that predates the first addon — @/ui/app/registries.test.ts now asserts real glob discovery (the tutorial addon is found) instead of emptiness.
- **The theme boot script in @/index.html is duplicated on purpose, and the CSP knows it** (ENG-391). It repeats `theme.ts`'s precedence as a synchronous inline `<script>` in `<head>` because a React effect runs after the first paint and a dark-theme user would see a white flash on every load; importing the module would mean waiting for the bundle, which is the thing being avoided. Both files carry a comment pointing at the other. The catch a future reader will not expect: @/security-headers.conf ships `script-src 'self'` with **no** `'unsafe-inline'`, so the inline script only runs in production because its **sha256 hash** is listed there. Editing the script changes the hash; @/ui/app/theme-boot.test.ts recomputes it and fails, because otherwise nginx would silently block the script and the flash would come back in production only. Vite copies inline `<head>` scripts into `dist/index.html` byte for byte (verified on the built output), so the source hash is the shipped hash.
- **The favicon is index.html's other static-asset contract, and nothing at runtime checks it.** @/index.html declares `<link rel="icon" type="image/svg+xml" href="/favicon.svg">` pointing at @/public/favicon.svg; Vite serves `public/` at the site root and copies it into `dist/` unchanged because @/vite.config.ts sets no `publicDir` (the default applies). @/ui/app/favicon.test.ts is the only thing that reads both halves together — it parses the `<link>` out of `index.html` and asserts the file it points to exists in `public/`, because a dangling href degrades silently to the browser's blank default, with nothing at runtime or in the build to catch it. The icon is the site mark (@/docs/design/website-icon.svg → @/ui/tokens/icon.tsx's `ColarIcon`) redrawn for 16px rather than cropped, and hardcoded to literal hex values rather than tokens because a `public/` file never passes through the bundler; its own `prefers-color-scheme` media rule (inside the SVG) covers the dark tab strip the way `ColarIcon`'s `onDark` prop covers it in React.
- The player container invariant is load-bearing: never swap the portal container — move the persistent holder node instead, or the whole player subtree remounts (react#12247) and playback dies on every station change.
- **The session player is mode-aware** (@/ui/app/audio-player.ts, ENG-275/ENG-247): in real mode `buildSessionPlayer` decodes the bucket's actual audio bytes with the @/adapters/audio `WebAudioEngine` — the AudioContext clock drives itself, no bridge. In fixture mode the bucket serves `PcmSpec` JSON that only the `FixtureAudioEngine` decodes, and its transport clock only advances through the rAF→`advance` bridge (`startClockBridge`). Both paths fetch the audio through the mode-aware `appBucket()` (@/ui/app/bucket-adapter.ts).
- Navigation never bypasses the gates: the stepper only calls `onNavigate` for `reachable` stations, and `App` funnels the `setMode` through `sessionStore.apply`, which is a no-op unless `canEdit()` (see @/ui/state/docs.md). Offline/review/lock therefore freeze station changes without losing state.
- Online state has two sinks on purpose: the local flag renders @/ui/organisms/connection-gate immediately, and `sessionStore.setOnline` pauses mutations — both fed from the `connectivity` port subscription AND from window `online`/`offline` events (`useOnline` adds/removes both, cleaning up in the effect teardown). The window bridge is what lets Playwright's `context.setOffline` drive the gate + pause with no app/fixture change (ENG-277) — the "small dev/test connectivity hook" kept entirely in the composition root.
- **`GET /projects` sits outside the contracts surface on purpose.** @/ui/app/bucket-adapter.ts's `listAllProjectIds` (the platform-admin fallback in `resolveProjectId`) is the only caller and reads the response with an inline cast, not a @/contracts/api.ts zod schema — the same style already used there for the `/audios` probe. `GET /projects` is not under the `/api/auth/*`/`/api/sound-necklace/*` scope @/scripts/api-snapshot.mjs filters into @/contracts/openapi.json, so it can't be schema-checked against that snapshot; this is accepted debt, not an oversight, and stays scoped to this one fallback path.
- **The app-global auth singleton** (@/ui/app/auth-adapter.ts, `appAuth()`, ENG-277/ENG-247): ONE lazily-memoized **mode-aware** provider shared by Login, Dashboard (@/ui/pages/dashboard/ports.ts `defaultAuth()` delegates to it) and the session root's `useAuthExpiry`. Because all surfaces hold the SAME instance, a single expiry trigger (or the login's own token) is observed everywhere — expiring mid-Triage has someone to notify. Real mode mounts the `HttpAuthProvider` (@/adapters/api/client.ts: email login, roles via my-roles, rotating refresh persisted in localStorage — §12 as amended by owner decision; see @/adapters/api/docs.md). `authReady()` (same module) is the **single-flight boot resume**: anything token-dependent awaits it before reading `appAuth().token()` — the session store's async token getter, the bucket's project resolution and the TTS 401 handler all queue behind it, so a reload cannot fire 401s while the persisted refresh is still becoming a session. `useAuthGate` (@/ui/app/auth-gate.ts + `App`) completes the story: in real mode, once the resume settles with no user, any route but login redirects to `/login` instead of running silently unauthenticated; the fixture never gates (tests/dev need no login).
- **The shared fixture backend is exposed** (@/ui/app/session-adapter.ts, `appSessionBackend()`, ENG-277): the fixture branch of the app-global `appSessionStore()` is built over this lazily-memoized `FixtureSessionBackend` singleton, exported so a test can build a SECOND `FixtureSessionStore` over the SAME backend as a different user — the only way to seed a foreign advisory lock (two Playwright browser contexts have separate localStorage otherwise). The real mode does not touch it.
- **Dev-only resilience test seam** (@/ui/app/test-seam.ts + @/ui/app/main.tsx, ENG-277 → acceptance-6 ENG-257): `installTestSeam()` attaches `window.__cds` with `expireAuth()` (→ `appAuth().simulateExpiry()`) and `seedForeignLock(id, holder?)` (acquires the lock via a second store over `appSessionBackend()` as user "Ana"). These are the two resilience triggers with no natural UI/localStorage path; offline needs no seam (`context.setOffline`). @/ui/app/main.tsx imports and installs it lazily ONLY under `import.meta.env.DEV`, so it never ships in the production bundle — the E2E webServer runs Vite dev, where DEV is true.
- **Shell copy now routes entirely through the dictionary** (ENG-279, @/ui/i18n/docs.md): the header, the review/lock banner (@/ui/app/review-banner.tsx) and the "estação em construção" fallback (@/ui/app/station-host.tsx) call `t()` directly. The fio-de-contas station labels stay data: @/ui/app/stepper-model.ts is i18n-free and emits a `labelKey` per station, which @/ui/app/stepper.tsx resolves with `t(labelKey)` — the model is derived from domain gates, so keeping copy out of it is what lets it stay a pure function. @/ui/pages/dashboard keeps its OWN copy of the six station-label keys (a separate array, since its step names differ from the stepper's) but reads the SAME `stations.*` translations, so the stepper can read PT while the dashboard glance reads EN. The one copy that still renders PT-BR under an EN UI is emitted by @/domain/@/contracts themselves (gate/error messages) — translating those is a frozen-layer change, out of scope for `ui/`.
