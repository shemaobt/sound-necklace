# Noridoc: conversation

Path: @/ui/pages/conversation

### Overview

- The conversation station (ENG-249): "Conversa (Conversation)" (PRD v2 §8.7, redesign §6.6). The whole mapping interview, **one question per screen**, in the exact order the domain produces: 11 level-1 questions → 5 level-2 per locked scene (none_fit included) → 5 level-3 per phrase of a productive scene.
- A wiring component: it reads the pure @/domain session through the @/ui/state session store, renders the @/ui/organisms `ConversationStage` (guide + Merriweather question + voice recorder + digit-free bead thread), and dispatches the mapping domain writes. The interview is **voice-only** (owner decision, design parity): there is no typed channel on this stage — typing lives only in the editable @/ui/pages/report card, after the conversation ends.
- Cream working stage, exactly one instruction line, no digits on the listener surface (§9.2). Each screen shows the ▶ of the relevant span ("ouvir a história / a cena / a frase").

### How it fits into the larger codebase

- **The station after Segmentação.** Stations self-register through the `import.meta.glob('/ui/pages/*/index.tsx')` registry built in @/ui/app/registries.ts, so the default export in `index.tsx` is the registry value, keyed by the directory name `conversation`. @/ui/app/App.tsx's `KEY_TO_MODE` maps `conversation` to the domain `conversation` mode; the shell renders this station when the session mode is `conversation`.
- **Question order is the domain's, not the UI's.** The flat screen order comes verbatim from `questionSequence` (@/domain/mapping.ts): L1 `L1_Q` → per `lockedParts` (none_fit included) `L2_Q` → per `productiveFrases` `L3_Q`. The UI never re-derives the order; it walks a single index across all levels.
- **The question TEXT follows the UI language; the artifact does not** (ENG-279). The screen renders `questionTextFor(slot, lang)` / `questionNoteFor(slot, lang)` (@/ui/i18n/conversation-questions.ts) — EN when the UI is EN, the domain PT-BR otherwise (also the fallback when a slot has no EN entry). The exported `.md` keeps serializing the domain PT-BR questions verbatim through @/contracts/relatorio.ts, so what the listener hears and what the Compilador reads can differ in language while staying the same question. Only the SEQUENCE and the `k` keys are shared, and both come from @/domain.
- **Answers.** This station only writes voice: it goes through the injected `VoiceRecorder` port (@/adapters/voice), keyed by the canonical `respostas/level{1,2,3}/…/<k>.webm` path from `voiceAnswerPath` (§10.4/O5) — the recorder owns persistence; the page never stores voice bytes in domain state. Typed answers (`setAnswer`, @/domain/mapping.ts — the lazy answer store that never loses answers across re-cuts/reopens, created/extended by `ensureMapping`, idempotent) are written by @/ui/pages/report, not here — see Things to Know.
- Reads session state via `useSessionStore` and writes only through `sessionStore.apply` (see @/ui/state/docs.md), so the store's editability gates (online/review/lock) can silently pause a write without losing in-memory state.
- Per @/.dependency-cruiser.cjs, @/ui/pages may import @/domain, @/ui/state, @/ui/organisms, @/ui/atoms, @/ui/tokens and adapters.

### Core Implementation

- **`Conversation({ player, recorder })`** (@/ui/pages/conversation/index.tsx): subscribes `session`; renders `null` until a session with a non-empty question sequence exists. Navigation is **screen scaffolding** — the domain does not persist `mapStep` (see @/domain/state.ts) — so the current question is a local index and the report is a local `atReport` flag.
- **Reading before the effect.** A `useMemo` derives `mapped` = `session` if it already has a mapping, else `ensureMapping(session)`, so answers render even before the mount effect persists the store. The mount effect calls `sessionStore.apply(ensureMapping)` once when `session.mapping` is null (guarded by the store's `canEdit`).
- **Resume follows the LAST answer, not the first hole** (ENG-321, corrected). On mount the cursor scans the sequence backwards for the last question that has either a text answer or a voice path in `meta.voice` (the `voicePaths` getter — a shell ref, read once at initialization, never in render), and opens on the question AFTER it; with nothing answered it opens on the first. When that last answer IS the final question the session reopens on the review instead — the conversation reached its end, and reopening on the last question invited re-recording an answer that already existed. It used to open on the FIRST question with no answer, which read a SKIPPED question as a pending one: skipping is deliberate — not recording is itself the answer, an empty one — so one skip early on became a permanent hole, and a session recorded up to the 40th reopened on the 2nd every single time. Skipped questions stay reachable through "← anterior" and the bead thread.
- **A session resumed into the review prepares itself.** The pre-review discovery (ENG-337) used to be triggered only by `goNext`, so reopening straight into the review never ran it and the screen sat on "Trazendo os áudios de volta" forever. A mount effect now runs it when — and only when — the session was RESUMED at the end; that flag is frozen as initial state, because recording an answer changes what the backwards scan returns, and `atReport` alone cannot tell a resume from a `goNext` transition.
- **The footer leaves with the transcription wait.** @/ui/pages/report signals `onWaitingChange` while its job runs and this station drops `.cds-conversation-controls` from the DOM — not `hidden`, which the stylesheet's `display: flex` would override in the browser while still passing a jsdom test. Under the wait the footer went on offering "Guardar os documentos →" with the drafts still in flight.
- **Navigation crosses levels by walking the index.** `goPrev` at index 0 dispatches `setMode('phrases')`; otherwise index−1. `goNext` at the last index sets `atReport`; otherwise index+1. Because the sequence is flat, a single index reproduces the reference `mapNav` boundary semantics (last L1 → first L2, first L2 prev → last L1, …) with no per-level special cases.
- **`QuestionScreen`** is a child mounted with `key={path}`: switching questions remounts it, so the recorder UI resets to `idle` by React's key rule (no synchronous setState-in-effect). Its one effect asynchronously checks `recorder.has(path)` and flips to `recorded` if a recording already exists. Record → `recorder.start(path)` (live levels feed the waveform) → `stop()` persists at `path`; "de novo" returns to `idle` and a fresh recording overwrites the same path; "ouvir" calls `recorder.play(path)`.
- **The question nobody answered is now recorded as such**, and the backwards scan counts it as answered. Walking backwards cures the hole in the MIDDLE of the interview; it cannot cure the hole at the END, which no scan can infer: when the last questions went unanswered, the last real answer sits upstream and the cursor lands on the first refusal, every reopen, with the review out of reach. `answered.ts` owns the mark — a reserved key in the answers bucket, the same design as `nota__` / `en__` / `src__` — read only by the UI and invisible to `buildMapReport`. The artifact still says `_(no answer)_` for an empty cell: declining and never being asked are the same thing to the pipeline, and a different thing to the facilitator. The stage's "sem resposta" toggle — under the mic hint, where the decision is actually taken — marks and advances (one decision, one tap), "voltar a perguntar" undoes without moving, recording clears the mark, and the recording lock covers it like every other control.
- **`QuestionScreen`** is a child mounted with `key={path}`: switching questions remounts it, so the recorder UI resets by React's key rule (no synchronous setState-in-effect). It resets to **`checking`**, not `idle`, whenever a `recorder` is supplied: "does this question already have an answer?" is a network round trip in real mode, and until it answers the screen does not know. It used to reset to `idle` — the invitation to speak plus the promise of a thread of sound, i.e. the *assertion* that there is no answer, on the very question that had one; whoever runs the interview reads that as loss. The effect settles `recorder.has(path)` to `recorded` or `idle` (a failed query settles to `idle`, as before — but now the wait actually ends). The settle is guarded on the state still being `checking`: someone who tapped the mic during the query is already recording, and a late "an answer exists" used to tear the live waveform out from under them mid-sentence. The mic is deliberately NOT disabled during the wait — it is the screen's one dominant action, and a network hop is no reason to refuse someone who wants to answer. Record → `recorder.start(path)` (live levels feed the waveform) → `stop()` persists at `path` and stores its `durationSec` as `answerSeconds`; "gravar de novo" goes through the organism's confirmation (ENG-392) and, once confirmed, `onRerecord` discards and starts a new recording immediately, overwriting the same path; "ouvir a resposta" calls `recorder.play(path)`. On mount, a `recorder.has(path)` hit also fetches `recorder.duration(path)` so the confirmation can name what is at risk; a failure there leaves it unknown rather than showing a made-up 0:00. Starting a recording first silences everything else that could bleed into the microphone — `player.stop()`, `speaker.stop()` and `recorder.stopPlayback()` (ENG-393) — and `onBlocked` wires the organism's refused taps to `UiSound.refuse()`.
- **Facilitator-led questions.** The `ausencia` items (both L1 and L2) pass `facilitatorLed` to the stage → the wordless role marker; every question's `note` renders as facilitator guidance.
- **The report handoff is add-a-file.** `ReportStation` is resolved once at module load from a static `import.meta.glob('/ui/pages/report/index.tsx')`; at the report step the page renders it when present, else a quiet placeholder. So the report screen (ENG-250) slots in without editing this station. It is handed the `recorder` — without it the report finds no recording and every card falls back to "ainda sem resposta gravada" — plus the `stt` port and `sessionId` (ENG-327), which the report needs for the per-session transcription job.
- **Transcription starts DURING the interview, on the way past each answer.** `goNext` fires `stt.start` for the current question when `meta.voice` says it was recorded. Advancing is the acceptance signal: the take was on screen, it could have been redone, and the facilitator moved on. Firing on `stop()` would pay for every take replaced before anyone moves — the very reason the job used to wait for the report — but waiting meant finishing the interview and then sitting through all 41 transcriptions at once. The call is fire-and-forget and its failure is swallowed: this runs on the way to the next question, and the interview is what must never stall on the network (ENG-338); @/ui/pages/report keeps its own idempotent trigger and picks up whatever a lost request left behind. A take redone AFTER advancing is not re-asked here — its draft is already `ready` and a plain POST leaves it alone, so the report resolves that one, which is where the durable record of which version was transcribed lives. **The wait screen does not disappear:** the last answer still starts transcribing on the way into the report, so the wait gets short rather than absent. The trigger keys on answers recorded **in this sitting**, not on `meta.voice`, which accumulates every answer ever recorded — keying on that made re-walking a finished interview fire one request per question, and a 14-scene session runs to ~396 of them.
- **The pre-review preparation discovers without downloading.** ENG-339 warmed every existing answer here so the review would open with the audio ready to play; at ~396 questions that is tens of megabytes fetched at once, of which a facilitator plays a handful. Audio now comes down on play, and the persistent cache (@/adapters/voice/cached-store.ts) makes the second play — and every reopen of the session — come off disk. The trade is a short wait on each answer's first play, against a long one and mostly wasted traffic when the review opens.
- **The report is not the end of the flow.** Its footer carries "Guardar os documentos →" (the prototype's `toExport`), which calls the `onGoToExport` prop. The tail (`export`) is LOCAL shell state — the domain has no `export` mode — so only @/ui/app/App.tsx can open it, and without that prop the report was a dead end reachable forward only through the header's stepper. Chrome is not an action; @/tests/e2e/full-cycle.spec.ts walks the button.

### Things to Know

- **Digit-free (§9.2).** No scene/phrase numbers on screen — the ▶ label ("ouvir a cena", etc.) carries the context. The ▶ that plays the current trecho's audio is wrapped in a `TrechoIndicator` (ENG-350 part 2): a colour dot + the trecho's kind name beside the button, from `currentTrecho` (@/ui/pages/conversation/trechos.ts) — same colour/name as that trecho's bar segment, a phrase inheriting its parent scene's kind. Progress is the per-_trecho_ bar (`ConversationProgressBar`, ENG-350): a continuous bar segmented história · cenas · frases, each in its colour, with a marker that slides across it and a caption naming the current trecho (a phrase inherits its parent scene's kind) — no counters, and it replaced the per-question beads. **How far along is the percentage, drawn** — each segment lights the fraction of it already reached, so the bar advances question by question *inside* a trecho; the owner asked for a numeric percentage and §9.2 forbids digits on a listener surface, so it is resolved in length instead. `aria-valuetext` puts the trecho label in place of the number for anyone listening to the screen. The `trechos` model is built by `buildTrechos` (@/ui/pages/conversation/trechos.ts) from `questionSequence`'s order. The one instruction line carries `data-role="instruction"`.
- **The audio/voice seam is the extension point.** `player` and `recorder` default to `null`; with neither, the page renders and navigates but playback/recording are dormant (same convention as the sibling stations). In production the shell injects both (@/ui/app/App.tsx): the session `Player` from `useSessionPlayer` and the real recorder built over the per-session answer store (@/ui/app/voice-adapter.ts — in real mode a `SessionVoiceStore` over the session's server-side resources, so a reload re-finds the recordings; see @/adapters/voice/docs.md).
- **No browser test.** This station has no `Necklace`/canvas geometry, so all tests run in jsdom (`conversation.test.tsx`): the full 11+5×2+5×2 sequence walk, per-level ▶ span play (player spy), the voice flow against the real `FixtureVoiceRecorder`, the role marker, the level-boundary navigation, and the §9.2 minimalism guard.
- **The page paints no background of its own during the conversation** (realigned to the Protótipo): `conversation.css` leaves the full-bleed olive to the shell's `.cds-app:has(.cds-conversation-stage)` selector (@/ui/app/app.css) and only tints its own text cream while that organism is mounted (`.cds-conversation:has(.cds-conversation-stage)`). At `atReport` the @/ui/organisms/conversation-stage organism unmounts, the `:has()` selectors stop matching, and both this page and the shell chrome fall back to cream automatically — no explicit "leaving ceremonial mode" state anywhere.
